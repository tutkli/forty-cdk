# forty-cdk — primitive authoring conventions

Detailed companion to the root `CLAUDE.md`. These auto-load when you edit library source (`projects/forty-cdk/**/src/**/*.ts` — every primitive entry point plus `forty-cdk/core`). Apply them everywhere; deviate only with a written reason.

## Linting (ESLint + Prettier)

ESLint (`eslint.config.js`, flat config) mechanically enforces the non-negotiables in the root `CLAUDE.md`: banned imports (`@angular/{cdk,material,aria}`, `zone.js`), banned syntax (`NgModule`, `@Input` / `@Output` / `@HostBinding` / `@HostListener` decorators, `Service` / `Component` / `Directive` class suffixes), the `for-` selector prefix on directives and components, SSR-unsafe `document` / `window` globals in library code, plus typescript-eslint hardening (`consistent-type-imports` with inline `import type` style, `no-explicit-any`, `no-unused-vars`). Run `pnpm lint` before committing — CI runs it on every PR — and `pnpm exec eslint . --fix` for auto-fixable rules. Prettier is configured (`.prettierrc`, `printWidth: 100`, single quotes); run it with `pnpm exec prettier --write <path>` when needed.

## Never propagate state inside `effect()`

**Never propagate state inside `effect()`.** Writing to a signal from inside an `effect` to derive another piece of state is an anti-pattern in modern Angular: it creates implicit cycles, double change-detection passes, and ordering bugs that are hard to debug. `effect()` is for **side effects** that escape the reactive graph (DOM imperative calls, subscriptions to non-signal sources, logging, focus moves that can't be expressed as host bindings). Reach for the right primitive instead:

- **`computed()`** — pure derivation from other signals.
- **`linkedSignal()`** — writable state derived from a source, with a reset rule when the source changes (the canonical replacement for `effect(() => mySignal.set(...))`).
- **`resource()` / `httpResource()`** — async state driven by a signal source (loading, error, value already modeled).
- **`toSignal()` / `toObservable()`** — bridge to/from RxJS without manual `effect`-based wiring.

If you genuinely need to write a signal from an `effect` (rare — usually integrating an external imperative API), document why in a comment and isolate it.

### The sanctioned-effect marker

"Document why in a comment" was for years the whole contract, which meant every review had to rediscover each carve-out's justification from scratch and no tool could tell a reasoned exception from an accident. There is now **one canonical marker**, and `forty-cdk/require-sanctioned-effect-marker` (`eslint.config.js`) fails `pnpm lint` on any `.set(` / `.update(` call inside an `effect()` callback in library source that is not covered by one. The marker is a comment on the line(s) immediately above the `effect(` call:

```ts
// @sanctioned-effect(<invariant>): <why the write cannot cycle>
effect(() => {
  out.set(measure(el));
});
```

- **`<invariant>`** is a short kebab-case name for the property that makes the write safe — it is the thing a reviewer verifies, and the thing a future refactor must preserve. The two shipped values are `external-source` (the written signal mirrors an imperative source outside the reactive graph, so nothing the effect reads can depend on it) and `untracked-read` (the effect reads the signal it writes through `untracked`, so there is no read-write cycle on it).
- **`<why>`** names the mechanism in one sentence, on the same line. Longer rationale goes in the function's JSDoc, where it already belongs — but do not repeat the marker's phrase there: only a **line comment whose text starts with it** is a marker ([#1606](https://github.com/tutkli/forty-cdk/issues/1606)), so a JSDoc quoting `@sanctioned-effect(<invariant>)` licenses nothing while still polluting the ledger a reader greps. The marker exists so that grepping `@sanctioned-effect` returns the library's complete carve-out ledger.
- **The marker licenses the effect it sits on, nothing else.** It is not a file-level or class-level opt-out, and a second `effect()` in the same function needs its own.
- **Reach for it last.** The marker is not a way to make the lint quiet — `computed()` / `linkedSignal()` / `resource()` / `toSignal()` cover every case that is really derivation, and a write that can be expressed with one of those is a rule violation whether or not it carries a marker. Four sites in the whole library qualify today, and both invariants are represented twice:

| Site                             | Invariant         | What makes the write safe                                                                                   |
| -------------------------------- | ----------------- | ----------------------------------------------------------------------------------------------------------- |
| `core/element-size`              | `external-source` | mirrors a `ResizeObserver`; the last box is held in a `prev` closure variable, never read back              |
| `virtualization/virtualizer`     | `external-source` | `notify` bridges `@tanstack/virtual-core`'s imperative `onChange` into the graph; the effect never reads it |
| `core/hover-intent/hover-intent` | `untracked-read`  | reads `open` through `untracked`, so it reacts to `disabled` alone                                          |
| `virtualization/infinite-scroll` | `untracked-read`  | reads both latches through `untracked`; tracks only `count` / `nearEnd`                                     |

The lint is deliberately syntactic, with two consequences worth knowing before you trust or fight it. It keys on the method name `set` / `update` and on **arity** — one argument only, because `WritableSignal.set(v)` takes one and `Map.set(k, v)` takes two ([#1606](https://github.com/tutkli/forty-cdk/issues/1606)). Arity is the whole of the signal-ness test, and all three rules of the family apply it, so "signal write" means one thing across them; a rule that tried to _prove_ signal-ness would need type information and would miss the real thing. What survives is a one-argument `.set(…)` on a plain receiver, and that false positive is loud, cheap to resolve here — the marker its author was already writing clears it — and preferable to a rule that misses the real thing. And, like `no-effect-state-propagation`, it does not descend into nested function scopes: a write inside an observer callback runs outside the effect's reactive run and is not counted. Writes that only touch the DOM (`setAttribute`, `toggleAttribute`, `style.setProperty`, `element.value = …`) are what `effect()` is _for_ and never trip it: the five DOM-only effects in `forty-cdk/core` carry no marker and should not gain one.

**Both rules follow a helper call one level deep, same file only ([#1575](https://github.com/tutkli/forty-cdk/issues/1575)).** A delegating helper used to hide the whole pattern from both rules — not just the write (`core/element-size` writes `out` from the `sync()` helper its effect calls, and the marker was required there by convention rather than by lint), but for `no-effect-state-propagation` the **read** too, and therefore the pairing it keys on: `effect(() => this.#sync())` presented as an effect touching no signal at all. That is how [#1572](https://github.com/tutkli/forty-cdk/issues/1572) shipped a self-retriggering effect through a green `pnpm lint`, and the failure mode is unusually expensive because the cycle is _synchronous_ — it blocks the Vitest worker's event loop, so there is no `testTimeout`, no stack trace, and no failing test, just a suite that goes from 58 s to ten silent minutes. So when an effect callback calls a helper whose declaration resolves in the same file — a method or arrow-valued field on `this`, or a function bound in an enclosing scope — that body is analyzed too and its reads / writes merged before pairing, with the report anchored on the call site and naming the helper.

**The residual gap is cross-file, and it is known rather than closed.** Resolution stops at the file boundary, so a method on an injected collaborator stays opaque — the #1572 cycle itself lived in `core/menu-overlay/menu-opener-registry.ts`, one file away from the trigger's effect, and would still slip through. Same-file and one level is the version that stays a lint rule instead of becoming a type-aware whole-program pass. **The marker is therefore still required by convention for a cross-file write**, so `grep @sanctioned-effect` stays the complete ledger — which is the whole point of having one phrase.

### The sanctioned-pull marker

An `effect()` can break the rule above in a second way that writes nothing at all: a **pull** — a read of a lazy store performed purely so the store's computation runs. Everything in the section above is about the write channel; this is the read one, and it needs its own marker because the shape it licenses is genuinely unavoidable.

**Why it cannot be derived away.** The stores behind every pull in the library are folds over a **transient** source: the set of mounted option / item handles, which is non-empty only while the consumer's `@if` keeps the collection rendered. A lazy derivation observes its source at the moment something reads it and at no other time, so a window that mounts and unmounts with no reader is lost with no trace (the `linkedSignal` mechanism is the one [#1518](https://github.com/tutkli/forty-cdk/issues/1518) documents: `previous` is only ever populated on a read). `prime()` is an `effect` used as a scheduler to guarantee that read — and [#1580](https://github.com/tutkli/forty-cdk/issues/1580) AC3's "no effect exists solely to force a lazy `computed` to run" is therefore unreachable for a fold over a transient source, which is what [#1602](https://github.com/tutkli/forty-cdk/issues/1602) resolved by sanctioning the shape instead of pretending it away. Deleting a pull breaks nothing a type, a signature or a review diff can see; the failure is silent and downstream (a selected label falls back to its serialized form value, off-window navigation stops resolving, `aria-activedescendant` lands on the wrong option).

The marker sits on the line(s) immediately above the `effect(` call, exactly like its sibling, and `forty-cdk/require-sanctioned-pull-marker` (`eslint.config.js`) fails `pnpm lint` on an unmarked one:

```ts
// @sanctioned-pull(navigator-position-map): the rendered window is transient, so
// a window nothing reads during is lost to the lazy fold.
effect(() => {
  runVirtualizedNavigatorBridge({ items, virtualized, requireNavigator });
});
```

- **`<store>`** is a short kebab-case name for the store being primed — the thing whose emptiness is the bug. Two values ship today: `label-cache-window` (Select / Combobox) and `navigator-position-map` (Select / Listbox / Tree / Combobox). **`<why>`** names, in one sentence, what makes the source transient.
- **A pull must not widen the tracked set of a write that shares its effect.** That is the invariant [#1600](https://github.com/tutkli/forty-cdk/pull/1600) paid for by hand: a pull drags the store's own sources into the effect, so pulling the label cache — which reads the selection — inside the auto-highlight bridge made every commit of `value` re-run that bridge's activedescendant write and `scrollIntoView`, and a hover-then-click could scroll the listbox to the hovered option (the fix was to split the pull into its own read-only effect). What the lint enforces is the **conservative syntactic proxy** of that invariant: a one-argument `.set(` / `.update(` in the same effect body as a pull is an error, and no marker clears it. The proxy is deliberately stricter than the invariant — deciding whether a store's sources are already a subset of what the write tracks is not something a syntactic rule can do — so the answer to a report is to split the effect, never to widen the rule.
- **When the reported "write" is not a signal, the rule has misread it — silence that line, don't restructure the code ([#1606](https://github.com/tutkli/forty-cdk/issues/1606)).** The proxy keys on a method name, so a plain collection trips it exactly the way `Map.set` trips the sanctioned-effect sibling — and here the resemblance stops being harmless: the marker that clears the sibling's false positive clears nothing on this branch, so an author with a legitimate scratch `Map` beside a pull has no move the docs bless. Two things make the choice non-arbitrary. **Arity settles the common case with no author action**: `WritableSignal.set(v)` takes one argument and `Map.set(k, v)` takes two, so only a one-argument call counts as a write. That condition arrived here, for this asymmetry, and then became the whole family's — "what counts as a signal write" cannot mean two different things across three rules that share a subject (do not push it further with type information; the family stays syntactic). **What survives is a one-argument `.set(…)` / `.update(…)` on a non-signal receiver** — a `WeakMap` cache, a builder — and its sanctioned resolution is an `eslint-disable-next-line forty-cdk/require-sanctioned-pull-marker` on the **write's own line**, with a comment naming the receiver, keeping the `@sanctioned-pull` marker in place. Scope it to the write line and it costs nothing else, which two things buy. The write branch reports **without returning**, so a suppressed misread still leaves the marker check to run. And it anchors on the **write itself** — inside the helper body when a same-file helper is what brought the write in, never on the call site the marker branches report against — so the two can never share a line. That second half is load-bearing and not free: fold a helper's writes onto its call site and both branches land on the one line, the prescribed disable silences them together, and nothing warns, because the directive is genuinely used. A blanket disable above the `effect(` is the wrong shape — it silences neither branch in the usual multi-line effect, so it reads as a licence while doing nothing.
- **One shipped pull does share its effect with writes: Combobox's. It is safe for the reason the proxy cannot check.** `runAutoHighlightBridge` pulls the position map and then writes activedescendant — through `tryResolvePending` on a resolve, through `seedFromIndexedSnapshot` on the passive seed — so it is exactly the shape the bullet above bans, and it passes lint only because those writes sit one file away (the residual gap below). It stays because the position map's sources (`items` / `totalCount` / the data version) are the ones that bridge already tracks through its own `items()` read, so the pull widens nothing; the label cache was the opposite case, which is why it has its own effect. `VirtualizedNavigator.tryResolvePending` is additionally built for this: its write is the pull's own settled result rather than foreign state riding along, and it reads its pending slot `untracked` precisely so the write cannot re-invalidate the calling effect. A new pull sharing an effect with a write owes that same two-part argument — the sources overlap, and the write is the pull's own result — spelled out where a reviewer can check it. Otherwise it goes in its own effect.
- **The rule names its cross-file runners rather than resolving them.** A pull is a call to `prime()` or to one of the free functions that exist to run one — `runVirtualizedNavigatorBridge` (`forty-cdk/core`) and `runAutoHighlightBridge` (`combobox/`). Write detection and same-file one-level helper resolution are identical to `require-sanctioned-effect-marker`, so the residual gap is the same: a write behind a cross-file collaborator call is invisible — which is what the Combobox bullet above relies on, and what a future cross-file write would slip through unnoticed.
- The complete ledger is `grep @sanctioned-pull`, mirrored row-by-row into the generated matrices at the end of this file. Six effects qualify today; a seventh needs a reason a reviewer can check against the bullets above. Write the marker's phrase **only** as a marker: the generated extractor keys on a line comment, but the grep does not, so a prose mention of `@sanctioned-pull(<store>)` in a JSDoc block reads as a seventh entry to anyone auditing the ledger by hand. Refer to it as "the sanctioned-pull marker naming `<store>`" in prose. **Both marker rules now key on the same anchor as the extractor** — a line comment whose text _starts_ with the phrase ([#1606](https://github.com/tutkli/forty-cdk/issues/1606)) — so a quoting JSDoc block or a mid-sentence mention is inert to the lint too. Before that, the match was a bare substring test over any nearby comment, and because the window is proximity-based (six lines above the `effect(`), a block that merely _documented_ a marker could silently license the next effect. The guidance above is unchanged and is now the smaller of two reasons to follow it: the hand-audit was always the loud failure, the silent licence was the expensive one.

**The four position-map pulls share one core helper.** Select, Listbox, Tree and Combobox all ran the identical four lines (`items(); if (!virtualized) return; prime(); tryResolvePending();`) in four entry points. `runVirtualizedNavigatorBridge` in `forty-cdk/core` is the single definition; it returns whether a pending navigation resolved, which is the one thing the Combobox bridge needs on top. Add a fifth virtualized collection by calling it, not by copying it.

## Assertions are dev-gated and live at the point of use

The third thing an `effect()` gets misused for, after the write and the pull, is **validation** — an effect whose whole body is a `throw` or an `assert*` call, watching a pair of inputs so it can object to their combination. It reads like the loudest possible failure and is close to the quietest one, so `forty-cdk/no-assertion-only-effect` (`eslint.config.js`) fails `pnpm lint` on the shape.

**A throw inside an `effect` never reaches the code that caused it.** Angular routes it to the application `ErrorHandler`: the stack names the effect scheduler rather than the binding at fault, the effect re-throws on every subsequent run, and an app with its own `ErrorHandler` — which most non-trivial apps have — swallows it entirely. Five sites shipped that way, and the one [#1583](https://github.com/tutkli/forty-cdk/issues/1583) was opened over had reached production as _silently degraded keyboard behaviour_: with `selectionFollowsFocus` set on a virtualized Select / Listbox / Tree, focus stopped carrying selection and nobody was told. A spec asserting `expect(() => fixture.detectChanges()).toThrow(…)` passed the whole time, because `ComponentFixture.detectChanges()` re-raises what `ApplicationRef.tick()` hands to the handler — the test proved the throw happened, never that a consumer would see it.

**So an invariant is asserted from its point of use: the call the invalid state degrades.** That call is the one with a stack a consumer can read, it fires on the interaction that is actually broken rather than on every re-run, and it needs no reactive node of its own. The three shapes in use:

| Where the invariant is checked                                           | Because that is where the invalid value…                                                                                                                                             |
| ------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Every keyboard move** (`selectionFollowsFocus`)                        | …changes nothing. `throwUnsupportedVirtualizedSelectionFollowsFocus` is called through each root's own `#assertSelectionFollowsFocusSupported()`, beside its `…RangeSelect` sibling. |
| The **derivation that consumes it** (column name / track, `granularity`) | …is interpolated into CSS (`ForTableBody.track`) or turns into segments an adapter cannot fill (`DateFieldEngine.specs`).                                                            |
| The **narrowing accessor** (`assertTimeCapable`)                         | …is about to be used: the assert returns the narrowed type, so it cannot be skipped.                                                                                                 |

**Two things about that first row are easy to get wrong, and both cost coverage rather than correctness.**

**"Every move" is the unit, not "the handler".** A keyboard handler has several branches and only some of them move focus, so a guard placed on the arrow branch alone leaves the other moves silently degraded with nothing reported — which is what the first cut of #1583 did: a consumer navigating a virtualized Listbox / Select by **typeahead**, or a virtualized Tree by **entering a child / leaving to a parent**, got the degradation and no error. Each root therefore funnels its moves through one private `#assertSelectionFollowsFocusSupported()` gated on `#virtualized() && selectionFollowsFocus()`, called from every move: the navigation branch and the typeahead match in Listbox / Select, and in Tree from `navigate` / `expandOrEnter` / `collapseOrLeave` / `handleTypeahead` — inside those four methods rather than in `onHostKeyDown`, because each is shared with the non-virtualized path where `[forTreeItem]` owns its own keys (the `#virtualized()` gate makes that path inert). Not every branch is a move: **expanding or collapsing in place moves no focus and degrades nothing**, so the guard sits after that branch, and seeding the activedescendant on focus / open is deliberately uncovered. Bounding the guard to real moves is what keeps the error honest; bounding it to one move is a gap.

**Moving the assertion does not, by itself, make the throw catchable.** Of the effect's three faults — unattributable stack, perpetual re-throw, swallowed by the consumer's `ErrorHandler` — the point of use fixes the first two unconditionally and the third only for the middle row of the table: a `computed` read during the render aborts the render, so `detectChanges()` re-raises it and a consumer's `try` sees it (that is why the table / date-field specs still assert `expect(() => renderHost(…)).toThrow(…)` unchanged). A **keyboard handler does not**: Angular wraps host listeners and routes their throws to the very same `ErrorHandler`, which is why the Select / Listbox / Tree specs capture through a real `ErrorHandler` instead. State the gain accurately when documenting a new guard — attributable and one-shot everywhere, catchable where the point of use is a render-time derivation — and do not promise a consumer they can `catch` an invariant asserted from an event handler.

Three rules follow, and the second is the one that keeps the ledger from growing:

- **Every assertion whose only audience is the developer is gated on `isDevMode()`** — inside the `assert*` helper itself, so the gate travels with the check and no call site can forget it. **The roster is generated**, both halves of it, in the matrices at the end of this file: which helpers gate themselves, and which do not. Do not re-spell either here — the prose version went stale inside the very PR that wrote it ([#1583](https://github.com/tutkli/forty-cdk/issues/1583) added two gated helpers and named neither) and had only ever recorded one of the two ungated ones. The **second row is the one to read**: an ungated assertion helper is legal only when it _narrows a type_, because the assert returns the narrow type and a production build that skipped it would carry on into a member that does not exist — `assertTimeCapable` into a `getHours` the adapter lacks, `assertTableDefRegistry` into a registration protocol the bound object does not implement. Any other name in that row is a policy violation, and `pnpm check:matrices --write` puts it in front of a reviewer rather than letting it accumulate. A directive's own `#assert*` method is a grouped call site delegating to one of these helpers, not a helper, and is deliberately absent from both rows.
- **An assertion beside real work is not this rule's business.** `[forTableColumnResizer]` asserts its column name inside the effect that publishes the width var — the assert sits at the point of use and the effect exists for the DOM write. Only an effect that does _nothing but_ validate is reported.
- **The one sanctioned assertion-only effect is `assertInputBound`, and the exemption is a condition rather than a path list**: an `effect()` inside a function whose own name starts with `assert` is a reusable assertion _scheduler_. That check has no point of use to move to — it asserts that a piece's binding was ever written, which is observable only _after_ the update pass, so the effect is the earliest possible read rather than a stand-in for one (see the `unsetInput` section above). Anything with a point of use must use it; naming a helper `assert*` to quiet the lint is the same defect as a marker written to quiet its sibling.

**One message, one definition.** The `selectionFollowsFocus` copy was pasted across three roots and had already drifted in two places by the time it moved. It now lives once in `core/typeahead/list-typeahead`, parameterised by the primitive name and the two hint fragments, exactly like the range-select throw it sits beside — add a fourth virtualized collection by calling it, not by copying it, and give that root the same single private `#assertSelectionFollowsFocusSupported()` so its own moves cannot drift apart either. The range-select twin was the standing counter-example (Tree carried a hand-written third copy, differing only in its "use `selectionMode="checkbox"`" remedy) and is folded in: the remedy is now the context's `alternative` fragment, so the rule ships with no exception.

## Every developer-facing message carries a `FORCDK-<AREA>-<NNN>` code

A consumer who hits a library error has one job — find out what they wrote wrong — and until now the library gave them a prefix and a sentence. The prefix said which entry point complained; nothing said _which_ complaint, so there was no stable handle to search for, quote in an issue, or link a docs page to. The scheme is one line per message:

```text
[forty-cdk/dialog] FORCDK-DIALOG-001: ForDialogTitle must be used inside a [forDialog] element.

Cause: No FOR_DIALOG_CONTEXT provider is visible from ForDialogTitle. Angular resolves a
directive's dependencies at the template's declaration site rather than where it is stamped, so a
piece declared in an ng-template outside the root resolves nothing even when it renders inside it.

Fix: Move ForDialogTitle inside a [forDialog] element, declaring any ng-template it lives in there too.
```

**Never build that string by hand.** `core/src/errors/` owns the layout, and everything the library reports goes through it:

| Helper                      | For                                                                                                                                                       |
| --------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `fortyError(spec)`          | returns the `Error` a call site throws — the general case                                                                                                 |
| `fortyWarn(spec)`           | a recoverable mistake, same layout, **dev-gated inside the helper**                                                                                       |
| `orphanContextError(spec)`  | a piece that resolved no coordination context — the library's most common report, ~70 call sites                                                          |
| `unresolvedRootError(spec)` | an overlay trigger that resolved its root through neither DI nor its own input — 9 call sites                                                             |
| `formatFortyMessage(spec)`  | the raw string, for the one seam that takes a pre-built message from its caller (`ElementRegistry.anchorSlot`, reached by Combobox / Select / TimePicker) |

Six rules govern a new message:

- **The code is stable and means one thing, forever.** Retiring a failure frees its number and reusing it is what the scheme exists to prevent, so numbers are sequential-ish per area but **not** gap-free. A code names one concrete failure; two call sites may share one when they are genuinely the same mistake arriving through two channels (`FORCDK-DRAWER-004` validates `closeThreshold` for both the `[forDrawer]` input and `ForDrawerManager.open`, from one shared validator — which is what keeps them from drifting).
- **The area is the entry point the consumer imported from**, kebab-case, upper-cased into the code: `forty-cdk/date-picker` → `FORCDK-DATE-PICKER-003`. The `[forty-cdk/<scope>]` prefix is **derived** from it, so there is one field to get right rather than two that can disagree.
- **`FORCDK-CORE-*` is for infrastructure that is genuinely no primitive's** — the root-context guard, the unset-input assert, the modal shell's backdrop registry, the virtualization/selection incompatibilities. Do not invent an area to make the scheme look tidier.
- **A shared check reports under the primitive that ran it**, via the `scope` override. `assertRootContext` is `FORCDK-CORE-007` and prints `[forty-cdk/accordion]`; the code says which check fired, the prefix says which primitive the consumer wrote. Two modules in core instead carry a _primitive's_ area because that is whose concern they are (`drawer-stack` → `DRAWER`, `menu-overlay/menu-context` → `MENU`); both are named conditions in the guard, not a blanket licence.

  **The override is a hand-typed entry-point name, so it is the one field the derived prefix did not remove** — and a typo in it prints `[forty-cdk/date_picker]` with nothing to notice. Every literal one is therefore checked against the set of directories the scan already walks, in the five shapes they are written in (`scope:` / `primitive:` / `entryPoint:` properties, an `entryPoint = '…'` field on a `ModalSurfaceBase` subclass, and `assertInputBound`'s second argument). A scope reaching a helper some other way is uncovered, and that is a known gap rather than a closed one. **Two blessed helpers take the override as an option rather than a positional string** — `injectDateAdapter(piece, { scope })` and `assertTimeCapable(adapter, piece, { scope })`, with an inline type so no new core symbol has to be blessed for one optional field — and both fall back to `core` for a caller that genuinely does not know an entry point: `serializeISODate`, whose branch is unreachable until `DateFieldEngine.specs` has already thrown the same code under the field's own scope.

- **`Cause` and `Fix` are omitted when they would restate the message.** A longer error is not a better one. `Cause` earns its place when the mechanism is not evident (which token resolved nothing, why a lazy fold is empty, why an ordering valid on paper collapses at this size); `Fix` when there is a concrete action. Several messages ship with a `Fix` and no `Cause`, and that is the intended shape, not an omission.
- **The gating does not change because the formatting did.** An orphan context throws unconditionally — without it the consumer gets a bare `TypeError` one line later in production — while a pure assertion stays gated on `isDevMode()` inside its own `assert*` / `throw*` helper, per the section above. `fortyError` deliberately does not gate; `fortyWarn` does, because a warning's whole audience is the developer.

The roster is **derived, never declared** — a hand-written list of a hundred-plus codes is the shape that rots. [`src/lib/error-codes.spec.ts`](../../projects/forty-cdk/src/lib/error-codes.spec.ts) scans library source and fails on a malformed code, a duplicated one, an area that does not name its entry point, a scope override that names no entry point, an emitter call with no code, a hand-built `[forty-cdk/…]` string, and a bare `console.warn`. It strips comments before scanning, for the reason the marker rules learned the hard way: a JSDoc example quoting a real code is prose, and counting it would report the helper as a second claimant of the code it illustrates. `grep -rn "FORCDK-" projects/forty-cdk` is the complete ledger.

Three of those cases are worth reading before trusting the guard, because each was a way it could have reported nothing:

- **The emitter scan reads a bounded body window, so the bound is pinned against the raw call count.** At 400 characters it silently skipped 18 of 128 calls — every one a message carrying both a `cause` and a `fix`, which is exactly where a field is easiest to forget — and the vacuum check (`> 100`, 110 at the time) could not tell. A window that is too small does not fail, it stops looking; the equality is what makes that loud.
- **Duplicate detection counts every site, not the set of files.** Two distinct failures sharing a code inside one module are the same defect for a consumer as two across modules, and deduping by file hid that half.
- **The hand-built-prefix case reports any `[forty-cdk/` literal outside the layout module**, not only one inside a `throw new Error(`. The throw-shaped version could not see the two that survived the first migration pass, because both were passed as an _argument_ to a core seam (`multipleAnchorsError`) and thrown one file away — with no code at all.

Nothing here reserves a URL. A future `/errors/FORCDK-DIALOG-001` page can key off the same codes without touching a call site, which is why no message embeds a link today.

## Form primitives use Signal Forms, never `ControlValueAccessor`

**Form primitives use Signal Forms, never `ControlValueAccessor`.** Any primitive that represents a form value (Switch, Checkbox, RadioGroup, Slider, Combobox, DatePicker, etc.) must implement the appropriate `@angular/forms/signals` interface so it auto-wires with the `[formField]` directive (selector `[formField]`, alias `formField`) — Angular detects the interface and binds everything, no provider/token registration:

- **`FormValueControl<T>`** for value-based controls. Required: `value: ModelSignal<T>`.
- **`FormCheckboxControl`** for binary on/off. Required: `checked: ModelSignal<boolean>`.

Both extend **`FormUiControl`** — expose its relevant optional members (`disabled`, `readonly`, `required`, `invalid`, `errors`, `touched`, `name`, `pending`, `min`/`max`/`pattern` where meaningful) as the prescribed `input` / `model` signals so field state flows in and out without consumer glue. Skip the members that don't apply to the control's shape (e.g. `min`/`max`/`pattern` on a Switch).

The stable contract reports touch interactions through the **`touch: OutputRef<void>` output** — `[formField]` listens to it and calls `markAsTouched()`; the `touched` input is write-only from the form's perspective (the form pushes field state down, it never reads the signal back). `FormUiControlBase.markTouched()` owns flipping the `touched` model (standalone `data-touched` reflection) and emitting `touch` together — primitives call it from every touch-producing interaction and never write `touched` directly.

`markTouched()` is deliberately **not** once-guarded — it emits `touch` on every touch-producing interaction, including repeats after the control is already touched. Deduplication is unnecessary and belongs nowhere in the library: Angular's `model()` setter bails on an equal value (so `touched` / `data-touched` / `(touchedChange)` already fire only on the first), and Signal Forms' `markAsTouched()` is an idempotent `selfTouched.set(true)`. A subclass override of `markTouched()` exists only to widen the base's `protected` visibility for a public `For<Primitive>Context` member, and must be a bare `super.markTouched()` pass-through ([#1393](https://github.com/tutkli/forty-cdk/issues/1393) item 12).

Every concrete form-value control also ships a `<name>-host-directive.ts` sibling exposing the `FOR_<PRIMITIVE>_HOST_DIRECTIVE_INPUTS` / `_OUTPUTS` tuples (re-exported from the primitive barrel) so wrapper components re-expose the full surface via `hostDirectives` without hand-maintaining the list — see `docs/wrapping-form-primitives.md`. The sibling's presence (and the barrel re-export) is enforced by the `forty-cdk/require-host-directive-sibling` ESLint rule in `eslint.config.js`; abstract bases like `TextValueControlBase` are exempt, the concrete subclasses own the contract.

The legacy `ControlValueAccessor` / `NG_VALUE_ACCESSOR` pattern is banned. Add `@angular/forms` as an _optional_ peer (`peerDependenciesMeta.optional`) so consumers using only non-form primitives don't pull it in.

`@angular/forms/signals` is stable as of Angular 22; the peer follows the standard major range (`^22.0.0`).

## Naming — accessible labelling & programmatic services

- **Accessible labelling.** Every primitive that exposes a reactive accessible name does so through one uniform input: `ariaLabel: input<string | null>` defaulting to `null`. Route it through the `hostAriaLabel` seam so a consumer's static attribute wins (see the static-attribute adoption section below) and host-bind the resolved signal — `protected readonly resolvedAriaLabel = hostAriaLabel(() => this.ariaLabel() || null)` host-bound `'[attr.aria-label]': 'resolvedAriaLabel()'` — which stays truthy-only, so a `null` or empty value on both channels emits **no** attribute. Put it on whichever piece carries the labelled role (the root for `Listbox` / `Menubar` / `NavigationMenu`, the content surface for `Dialog` / `Drawer` / `Select` / `Combobox` / menu roots). This is just a reactive convenience over the native attribute: consumers who have a visible label element should still prefer pointing native `aria-labelledby` at it (the directive defers to `aria-labelledby` and emits no `aria-label` when its value is falsy). Combobox is the documented exception that needs no separate hook discussion — it still follows this `ariaLabel` shape. Do not invent per-primitive variants (`label`, `aria-label` attribute only, `input<string>` default `''`).
- **Never ship a hardcoded English literal in an `aria-*` (or `aria-valuetext`) host binding — route the default through the primitive's scope defaults so it is localizable.** A screen reader verbalizes these strings, so an English literal baked into the directive announces English in every locale with no way out ([#1159](https://github.com/tutkli/forty-cdk/issues/1159)). The two sanctioned shapes:
  - **A piece that _needs_ a non-null default accessible name** (icon-only controls like `[forComboboxClear]` / `[forSearchClear]`, or a labelled grouping region like `[forComboboxChips]`) still exposes the uniform `ariaLabel: input<string | null>`, but defaults it to the scope's defaults key rather than to `null` or a literal: `readonly ariaLabel = input<string | null>(this.#defaults.clearAriaLabel)`, host-bound through the same `hostAriaLabel` seam. The defaults key (`clearAriaLabel`, `chipsAriaLabel`, …) holds the English fallback and is overridable per scope via `provideFor<Primitive>Defaults`; a per-instance `[ariaLabel]` still wins, and `[ariaLabel]="null"` still drops the attribute. This is a deliberate, documented departure from the "defaults to `null`" rule above — the accessible name is mandatory here, so the localizable default replaces the null one. Every other piece has an optional name and keeps `null`; the full roster of non-`null` defaults is in the generated matrices at the end of this file, and the key it reads is listed with it. **The key follows the `*AriaLabel` scheme** — `clearAriaLabel`, `chipsAriaLabel` — so a defaults interface reads as "this key names a widget" rather than "this key is a caption". `[forBreadcrumbs]` is the one deviation: its key is `ForBreadcrumbsDefaults.label`, kept because renaming a published defaults key is a consumer break and the trail has no second label-ish tunable to confuse it with. Do not copy it; a new defaults-backed accessible name uses `*AriaLabel`.
  - **A computed accessible string with no per-instance input** (`[forStepperProgress]`'s `aria-valuetext`, `[forCarousel]`'s positional slide / indicator labels) routes through a **builder function** on the defaults interface — `stepValueText: (current, total) => string`, `slideLabel: (position, total) => string` — so a consumer localizes it centrally by overriding the function. Keep the default builder producing the same English string it did before.
- **Programmatic services**: when a primitive ships an injectable for opening / coordinating overlay instances imperatively (Dialog today; future Toast / Snackbar / HoverCard programmatic), name it `For<Primitive>Manager` and put it in `<primitive>-manager.ts`. The per-instance handle stays `For<Primitive>Ref`. Avoid plural class names (`ForDialogs`) — they collide visually with the directive (`ForDialog`). The `Service` suffix is still banned; `Manager` describes the role (lifecycle + stack of instances), it isn't an empty category tag.
- **Spelling: the library says _dismissible_, never _dismissable_ — and never _closable_.** One vocabulary for "the user can make this go away": the overlay input is `dismissible` on all twelve primitives that expose one (Dialog, Drawer, Toast, Popover, Select, Combobox, DatePicker, TimePicker, ContextMenu, DropdownMenu, Menubar, MenuSub), the core layer family is `DismissibleLayer` / `DismissibleLayerStack` / `injectDismissibleLayer` in `core/dismissible-layer/`, and the menu context's exemption list is `dismissibleExemptions`. Toast's `closable` input (plus `ForToastConfig.closable` and `ForToastContext.closable`) and the misspelled `Dismissable*` family were both retired in [#1400](https://github.com/tutkli/forty-cdk/issues/1400) — pre-1.0, with no deprecated aliases. Never introduce a second spelling or a `closable` / `closeable` synonym for the same concept.

### Public type aliases stay unprefixed (`For` prefix is for runtime symbols only)

The `For` prefix marks **runtime symbols** — directives / components (`ForAccordion`, `ForSelectOption`), injection tokens (`FOR_SELECT_CONTEXT`), provider helpers (`provideForToastDefaults`), and the context / handle interfaces a piece injects (`ForSelectContext`, `ForComboboxOptionHandle`, `ForToastDefaults`). Plain public **type aliases** that name a value-set or a configuration shape stay **unprefixed** (decision **D12** of [#556](https://github.com/tutkli/forty-cdk/issues/556)). This is a deliberate, documented exemption — not an inconsistency to "fix" by renaming. Renaming these to `For…` before 1.0 would churn the public surface for no semantic gain: a string-literal union or a granularity enum is not a forty-cdk runtime construct the way a directive or token is.

Types covered by the unprefixed exemption today: `HoverCardScheduleReason`, `TooltipScheduleReason`, `NavigationMenuScheduleReason`, `TabsActivationMode`, `SliderArrowKey`, `DateFieldSegment`, `DateSegmentType`, `SegmentType`, `FieldGranularity`, `TimeFieldSegment`, `TimeSegmentType`, `TimeGranularity`, `CalendarWeek`, `CalendarWeekday`, `CalendarDayCell`, `DateRange`, `OtpInputType` (plus the adapter / standard-vocabulary types `DateAdapter`, `TimeCapableDateAdapter`). New primitives follow the same split: prefix runtime symbols and injected contracts, leave plain public type aliases bare.

### Naming exceptions (coordination tokens)

A primitive's per-instance coordination token / interface is normally `FOR_<PRIMITIVE>_CONTEXT` / `For<Primitive>Context`, resolved through an `inject<Primitive>Context` helper. **Number-input** intentionally diverges: the cross-piece coordination it needs is not the spinbutton-to-children context but a **group registry** — the void `<input>` carrying the spinbutton can't contain the `[forNumberInputIncrement]` / `[forNumberInputDecrement]` buttons as DOM descendants, so they coordinate through `[forNumberInputGroup]`. The token is therefore `FOR_NUMBER_INPUT_GROUP` (a `_GROUP` suffix, resolved via `injectNumberInputGroup`), reflecting that it is a registry of a registered field rather than a per-instance context. `ForNumberInputContext` (the spinbutton's surface read through `group.field()`) keeps the standard name. This mirrors the treatment the _Documented alternative vocabularies_ table gives ScrollArea / Avatar / etc.: a named, justified exception rather than a silent one.

**Search takes the same exception, for the identical reason.** `[forSearch]` is a void `<input>` too, so `[forSearchClear]` cannot inject the field as a DOM descendant and coordinates through `[forSearchGroup]` / `FOR_SEARCH_GROUP` / `injectSearchGroup`, with `ForSearchContext` keeping the standard name for the field's own surface. The two are one pattern, not two exceptions: **a form primitive rooted on a void element expresses its cross-piece coordination as a `_GROUP` registry**, and both the token and its resolver are public (see the taxonomy below). A third void-rooted primitive follows the same shape rather than inventing a name; anything with a container root uses the plain `_CONTEXT`.

### Context exports — what's public

The **`FOR_<PRIMITIVE>_CONTEXT` token + its `For<Primitive>Context` interface stay exported** from the barrel for advanced consumers who legitimately need to inject the coordination surface (custom pieces, headless re-composition). The **`inject<Primitive>Context` resolver helper is internal** — unexported from every barrel ([#626](https://github.com/tutkli/forty-cdk/issues/626)) — because it is a piece-authoring convenience (throws a primitive-prefixed orphan error), not part of the consumer-facing API. This split is uniform across the anchored overlays (Popover / Tooltip / HoverCard) and every other primitive: do not export `inject<Primitive>Context`, and do keep the token + interface exported. A primitive whose context is purely an implementation detail (no advanced-consumer use case) may keep both the token and the interface module-internal, but it must do so consistently with its sibling primitives rather than exporting one and hiding the other.

#### The resolver taxonomy — which `inject*` helpers are public

The library exports a dozen `inject*`-shaped functions and hides a dozen more, and until now the split was folklore. There are exactly **three tiers**, and a new helper belongs to one of them before it is written:

| Tier                    | Shape                                                                                 | Public?                                                             | Today                                                                                                                         |
| ----------------------- | ------------------------------------------------------------------------------------- | ------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| **Context resolver**    | `inject<Primitive>Context(piece)` — resolves `FOR_<PRIMITIVE>_CONTEXT`, throws orphan | **Hidden** ([#626](https://github.com/tutkli/forty-cdk/issues/626)) | every primitive's own                                                                                                         |
| **Group registry**      | `inject<Primitive>Group()` — resolves a `FOR_<PRIMITIVE>_GROUP` registry              | **Public**, with the token                                          | `injectNumberInputGroup`, `injectSearchGroup`                                                                                 |
| **Consumer composable** | a headless capability the consumer calls in their own component                       | **Public**, with a README section                                   | `injectBreakpoints`, `injectVirtualizer`, `injectInfiniteScroll`, `injectDialogData`, `injectDrawerData`, `injectFieldWiring` |

The distinctions that decide the tier:

- A **context resolver** is a _piece-authoring_ convenience. Its whole value is the primitive-prefixed orphan `Error`, which only makes sense to someone writing a directive that must sit inside the primitive; the supported consumer channel for the same coordination surface is `inject(FOR_<PRIMITIVE>_CONTEXT)`, which the barrel does export. Exporting the resolver would publish a second path to the same thing with a friendlier error, and the friendlier error names an internal piece name the consumer does not have. **A public token's JSDoc therefore must not `{@link}` its resolver** — the symbol is absent from the emitted `.d.ts`, so the link is dead exactly where the JSDoc is read, at the consumer's `inject(FOR_<PRIMITIVE>_CONTEXT)` call site. All eight split roots did it, and two of them (`radio-group`, `select`) additionally linked an internal `<X>Context` the flattening had dropped; what a guarded token's block owes instead is the `useExisting` precondition, gated in [`root-context-guard.spec.ts`](../../projects/forty-cdk/src/lib/root-context-guard.spec.ts) by the pattern that a `{@link …Context}` must be `For`-prefixed to be public.
- A **group registry** is public because the token is. The registry exists so a piece _outside_ the root's DOM subtree can coordinate (the void-element case above), and a wrapper re-providing the group needs both the token and a way to read it — so hiding the resolver would leave the exported token half-usable. This is why the `_GROUP` naming exception carries a public resolver while `_CONTEXT` does not: different reachability problem, different answer.
- A **consumer composable** is the primitive itself. `injectVirtualizer` _is_ `forty-cdk/virtualization`; `injectBreakpoints` _is_ `forty-cdk/breakpoints`; `injectDialogData` is how a dialog component reads what opened it. These need JSDoc written for consumers and a README, exactly like a directive.

**A cross-entry-point resolver stays in the core internal tier — it is exported from `forty-cdk/core` and that is not a violation.** `injectMenuContext` is the case: `forty-cdk/menu`'s pieces resolve the shared menu context through it, and a cross-entry-point import must go through the `forty-cdk/core` specifier (never a relative path), so the barrel export is mechanically required. What keeps it non-public is the tier, not the barrel: it is absent from `CORE_PUBLISHERS`, so `check-entrypoint-public-types.mjs` already fails the build if any stable entry point re-exports it or surfaces it in a signature. Contrast the context _interface_ `ForMenuContext`, which is deliberately blessed and published by `forty-cdk/shared` because advanced consumers do inject it. Removing the resolver from the core barrel — the fix [#1401](https://github.com/tutkli/forty-cdk/issues/1401) item 4 originally called for — would simply break `forty-cdk/menu`; the tiering introduced by [#1398](https://github.com/tutkli/forty-cdk/issues/1398) is what actually resolved it.

**A blessed core type is published by exactly one entry point, and never re-exported by the barrel that merely uses it.** Those exported context interfaces (and any other public signature) legitimately reference cross-primitive types declared in `forty-cdk/core` — `RovingTabindex` / `ListNavigationAction` (roving + keyboard navigation), `SegmentEditorContext` / `SegmentHandle` / `FieldSegment` (date/time fields), `ForMenuContext` & friends (menu family), `DragPreview`, `ElementBox`, `Point`, … — and consumers import every one of them from **`forty-cdk/shared`**, the entry point that publishes the blessed tier ([#1486](https://github.com/tutkli/forty-cdk/issues/1486)). A primitive's own barrel must **not** re-export them. Until #1486 the opposite rule held ([#1140](https://github.com/tutkli/forty-cdk/issues/1140) / [#1180](https://github.com/tutkli/forty-cdk/issues/1180) required a local re-export of every core type a signature surfaced): 37 barrels carried the same 38 symbols — `WritingDirection` alone in 29 of them — and each symbol was reachable from two specifiers with two different stability guarantees. Six blessed symbols keep a primitive as their canonical publisher because it is their semantic home rather than a duplicate path: `ForVisuallyHidden` (`forty-cdk/visually-hidden`), `ForDrawerSide` (`forty-cdk/drawer`), and the field-wiring set `FOR_FIELD_CONTEXT` / `ForFieldContext` / `FieldControlHandle` / `injectFieldWiring` (`forty-cdk/field`). The publisher of each blessed symbol is recorded in `CORE_PUBLISHERS` ([`scripts/lib/core-blessed-tier.mjs`](../../scripts/lib/core-blessed-tier.mjs)) and enforced in both directions by the gate. The alternative to blessing is unchanged: narrow the leak so no core symbol crosses the boundary (drop the member, make it `protected`, or retype it to a minimal local shape).

### The public context carries only what a consumer reads or invokes ([#1399](https://github.com/tutkli/forty-cdk/issues/1399), [#1722](https://github.com/tutkli/forty-cdk/issues/1722))

A `For<Primitive>Context` is the **consumer read surface**, and the rule is stated as an **inverted default**: it lists _only_ signals a consumer reads and commands a consumer invokes. **Every member whose sole caller is a piece of the same primitive lives on the unexported `<Primitive>Context` interface and is TS-`private` on the root** — the mechanism below, not a naming pattern. The reason is semver: the wiring between a root and its pieces is the code the library refactors most (`registerVirtualWindow` arrived in [#1334](https://github.com/tutkli/forty-cdk/issues/1334)), and the wrapping patterns the library supports guarantee a public one gets discovered and used. Pre-1.0 the members simply disappear; after 1.0 each one would be frozen.

**The default is inverted because the previous phrasing named the members instead of the property, and a name is what a new root routes around.** #1399 said "the piece-registration protocol — `register*` / `unregister*` / `set*` and the read-backs that exist only to serve them", so the split caught exactly the members whose identifiers matched. Everything else stayed, and `ForComboboxContext` shipped **77** members: `emitPointerDownOutside` (called by `injectOverlayShell`), `setQueryFromInput` (by `[forComboboxInput]`), `moveActionFocus` (by `[forComboboxAction]`), `isPointerSuppressed` (by `[forComboboxOption]`), every positioning mirror `[forComboboxContent]` feeds to floating-ui, both label caches, both navigation cursors. Not one of them is something a consumer calls, and not one matched the pattern the split searched for. `ForAvatar.reportStatus` was the same defect at its smallest — a public method whose JSDoc said _"Consumers should not call this"_, which is a prohibition with no mechanism.

**The ceiling is the gate, and it is a smell detector rather than a budget.** `scripts/check-context-surfaces.mjs` (`postbuild`) fails on a published `For*Context` above **25 members**, counting the _flattened_ surface — own members plus everything it inherits, because a consumer reads one surface off the token either way. Twenty-five is not a target to spend down to; it is the point at which a context stops reading as "what a consumer does with this primitive" and starts reading as an inventory of its internals, which is the signal that the inverted default was not applied. A root that genuinely needs more is an **entry in `scripts/lib/context-surfaces.mjs`** carrying a written reason and its own tighter bound — never a raised ceiling, which would make the gate decorative for every root at once. The gate reads an entry in both directions: it fails when the surface grows past the recorded bound, and it fails when the surface drops to the global ceiling and the entry is left behind, so the list can only drain.

Ten roots are split today. Table / Select / Combobox landed with #1399, Accordion / Carousel / RadioGroup / Tabs / Toast followed in [#1524](https://github.com/tutkli/forty-cdk/issues/1524), and NavigationMenu joined them in [#1530](https://github.com/tutkli/forty-cdk/issues/1530). #1722 then re-cut four of those under the inverted default — Combobox (77 → 22), Select (51 → 16), Carousel and Table — and split Avatar as the tenth, which is the count [`root-context-guard.spec.ts`](../../projects/forty-cdk/src/lib/root-context-guard.spec.ts) derives. The ten interfaces still listed in `context-surfaces.mjs` are the roots it has not reached; each is pinned at its current size, and none of them is argued to be legitimately wide. A new composed primitive is authored split from the start.

**A split root's own class members follow, and the naming is deliberate.** The unexported interface is composed rather than monolithic: `<Primitive>RegistrationContext` for the `register*` / `unregister*` / `set*` protocol where one exists, `<Primitive>PieceContext` for everything else a piece reads off the root, and `<Primitive>Context extends For<Primitive>Context, …` as the type `inject<Primitive>Context` returns. All of them go in `scripts/lib/registration-surfaces.mjs`, whose gate is what keeps a moved member from coming back. `private` erases a member's _type_ from the emitted `.d.ts` and leaves a bare `private moveActionFocus;` placeholder behind — that placeholder is the mechanism working, not a leak: the member is uncallable and unnameable, and the same line has been there for every `register*` since #1399.

**Narrowing the interface does not narrow a consumer's binding surface, which is why the cut can be this deep.** A positioning mirror like `sideOffset` is an `input()` on the root and stays public there — Angular's `strictInputAccessModifiers` requires it, and it is the consumer's API. What leaves is the _context_ member, which only ever existed so `[forComboboxContent]` could read the value it was bound with. Combobox keeps one member the read published only for a consumer: `invalidateSnapshot`, the imperative twin of the `[dataVersion]` input, which no piece calls and which `ForListbox` / `ForTree` publish under the same name.

**The default costs one interface, and the expensive shape is the exception ([#1593](https://github.com/tutkli/forty-cdk/issues/1593)).** The mechanism, per primitive:

- **One token, two typed views.** `FOR_<PRIMITIVE>_CONTEXT` + `For<Primitive>Context` stay exported. A second **interface** — `<Primitive>Context extends For<Primitive>Context` — carries the protocol and is **never** listed in `public-api.ts`; `inject<Primitive>Context`, already internal and already the single chokepoint every piece resolves through, reads the same token at that type. So the root's `providers` are the one line every _unsplit_ root already writes (`[{ provide: FOR_<PRIMITIVE>_CONTEXT, useExisting: For<Primitive> }]`), and the split is invisible to a wrapper.
- **The root class must not re-publish what the interface dropped.** `ForTable` / `ForSelect` / `ForCombobox` are exported classes, so a `register*` method on them is callable (and frozen) regardless of the interface split. Three sanctioned ways to keep it out of the emitted `.d.ts`: extract the state into its own provider (`TableRegistry`, provided by `[forTable]` and reached through the registration token — the shape to reach for when the state is genuinely separable), declare the member with the **narrow** public type (`ForSelect.overlay: ForSelectOverlayFacade`, with the full controller reachable only at the internal interface's type), or mark the method TS-`private` (its type is erased from the `.d.ts` while `useExisting` still satisfies the internal contract at runtime — the pragmatic option for thin delegating methods, as in `ForCombobox`, `ForTableRow.registerCell`, and all ten pairs of the five #1524 roots). `protected` also counts as non-public — both gates skip protected / private members.
- **A second token is for a protocol that cannot be a view of the root, and Table is the only one.** Two conditions put it there, and Table meets both: the protocol **crosses an entry-point boundary** (`core/table-registration/`, because `forty-cdk/table-virtualization`'s `[forTableVirtualized]` registers through it — a token exported only from `table/src` would be unreachable there), and it is aliased to a **separate provider** rather than to the root (`TableRegistry`, which `[forTable]`'s own constructor injects). Being un-blessed core, `check-entrypoint-public-types.mjs` already fails the build if the protocol leaks — which is why the handle / seam types (`ForTableRowHandle`, `ForTableCellHandle`, `TableVirtualWindow`, `TableVirtualRow`, `TableVirtualRowNavigation`) moved there too.
- **A same-entry-point protocol is listed in the gate.** `scripts/lib/registration-surfaces.mjs` names the surface symbols per entry point and `scripts/check-registration-surfaces.mjs` (`postbuild`) fails when one is re-exported from the barrel or reaches an exported declaration's public signature. It also fails when a listed name no longer exists in that entry's source, so the list cannot rot. Add the internal interface and its handle types when you split a new primitive's context.

**A second token only retypes what `private` already hides, and it drags three more artefacts in with it.** #1399 / #1524 / #1530 shipped one per split root, and #1593's audit found all eight aliased to the **same object** as the public token (`useExisting: root` twice) and named from exactly **two files**: their own context module (declaration + resolver) and the root's provider helper. Retyping is all they ever did. What they cost is the chain: Angular does not inherit a directive's `providers`, so a subclass replaces the array wholesale — and the moment a root provides a **second, unexported** token, the hand-written re-provide `docs/wrapping-non-form-roots.md` prescribes is both insufficient and _unwritable_, which forced a `provideFor<Primitive>(root)` export, a positive `<primitive>-wrapper.spec.ts` guarding it, and a roster line for the token. So: **do not reach for a second token to express "these members are not public".** Reach for it when the protocol must be reachable from another entry point, or when the state is separable enough to be its own provider — the two conditions above.

**What one token leaves behind is an unchecked cast, and the answer is a guard rather than a second token ([#1669](https://github.com/tutkli/forty-cdk/issues/1669)).** The token is declared at the **read** surface and `inject<Primitive>Context` reads it at the internal interface's type, so a consumer who provides it with anything else satisfying the public type typechecks, resolves, and then fails inside the first piece to reach the protocol — a bare `TypeError`, no `[forty-cdk/<entry>]` prefix, a stack pointing at a library file for a mistake made in consumer providers. Before the collapse the same markup produced the primitive's own orphan error, because the token the resolver read was simply absent; that is the residual half, and it is **strictly smaller than the hazard #1593 removed** (a fake public token under a real ancestor root resolved the two tokens to _different objects_, so a consumer read one surface while the pieces silently wired into another). `assertRootContext` (`forty-cdk/core`) closes it from the chokepoint every piece already resolves through: one call per resolver, dev-gated inside the helper, throwing the prefixed error the orphan branch throws and naming `{ provide: FOR_<X>_CONTEXT, useExisting: MyRoot }`. Four things about it are the ones to carry to the next split root:

- **There is no compile-time channel, and that is settled rather than unexplored.** The roots declare `implements For<Primitive>Context` only; a `satisfies <Primitive>Context` cannot be added because the protocol members are TS-`private` (`TS2322: Property 'registerTrigger' is private in type 'ForAccordion' but not in type 'AccordionContext'`). Keeping the members out of the emitted `.d.ts` and coupling the class to the internal interface are mutually exclusive, so a runtime probe is the only channel there is — do not re-propose the type-level one.
- **The probe is supplied per call site, because the internal interface does not always add a `register*`.** Most roots probe one; **Select adds none** — it widens `overlay` from `ForSelectOverlayFacade` to the full controller — so its probe is nested (`overlay.setInitialFocus`, a member the controller has and the facade does not). A probe that _throws_ counts as a miss, so a value missing the whole nesting level still fails with the library's error instead of the read's `TypeError`. The roots #1722 split probe a piece member instead (`ForTable.cellTabIndex`, `ForAvatar.reportStatus`), which is the same test: a member the read surface does not declare.
- **The two trigger resolvers guard on read, not at injection.** Their explicit-root path (`[forSelectTrigger]="root"`) resolves inside a `computed`, so the assertion sits there and covers both paths at once — and that path was an unchecked widening _before_ #1593, so the guard closes something older than the collapse.
- **The roster is derived, in [`src/lib/root-context-guard.spec.ts`](../../projects/forty-cdk/src/lib/root-context-guard.spec.ts), from "this module declares `interface <X>Context extends For<X>Context`"** — exact in both directions today, with the per-module call count asserted too so a _second_ resolver added to a module that already guards one cannot slip in unguarded.

**The wrapper specs stayed, retargeted.** Each split root keeps a `<primitive>-wrapper.spec.ts` mounting a real subclass, but its `providers` are now the hand-written one-liner — so the spec proves the cheap shape is sufficient instead of guarding a helper. The **negative** half (a hand-written list fails, and with an actionable error rather than a bare `NG0201`) survives only where a `provideFor*` helper does: `table-wrapper.spec.ts` and `table-body-wrapper.spec.ts`, which are together the executable record of why Table is the exception.

**A split root that is a _component_ is exempt from the positive half of that guard, because subclassing it is not a wrapping shape at all ([#1563](https://github.com/tutkli/forty-cdk/issues/1563)).** Angular inherits a base's `providers` no more generously for a component than for a directive, but it also inherits neither `template` nor `imports`: a subclass declaring its own `@Component` renders its own template and nothing of the base's — so a subclassed component root constructs successfully and renders nothing, unless the consumer copies the inline template the library refactors freely. The exemption survives #1593 unchanged because it is about the _template_, not about the provider set: it would hold just as well for a component root whose providers are the one-line re-provide. `<for-table-body>` is the first instance: its `provideForTableDefRegistry()` is public (a scaffold wrapper must provide the registry on its own host — see the reachability rule below), its supported wrapping shapes are both **compositional** (a preset column component, a scaffold wrapper projecting defs), and the guard that proves the helper complete is therefore the composition spec [`def-registry.spec.ts`](../../projects/forty-cdk/table/src/def-registry.spec.ts) rather than a subclass spec. `table-body-wrapper.spec.ts` still exists and still carries the **negative** half — a hand-written provider list must fail with a `[forty-cdk/table]`-prefixed error naming the helper, never a bare `NG0201` naming the unexported registry class — plus the executable record that the helper-provided subclass renders none of the body. A future composed component root inherits this answer: name its composition spec, keep the negative case, and do not write a positive subclass case.

Narrowing, not deleting, is the fallback: a member a consumer genuinely needs stays on the read surface (`focusedRowIndex`, `loadedRowCount` and `rowCount` all did). A member the split misclassified moves back: `registerAnchor` / `unregisterAnchor` are on the **public** surface of Select (through `ForSelectOverlayFacade`) and Combobox, because a consumer whose anchor element lives in an ancestor component's template cannot use the declarative `[forSelectAnchor]` / `[forComboboxAnchor]` — a directive there resolves DI outside the root — so imperative registration is the only channel and belongs with `openMenu` rather than with the wiring protocol.

**A registry a _wrapper_ must be able to provide is public — the token, a read interface, and a `provideFor*` helper, never the protocol.** `FOR_TABLE_DEF_REGISTRY` ([#1372](https://github.com/tutkli/forty-cdk/issues/1372)) is the case, and it reads at first glance like the opposite of this rule. `<for-table-body>`'s four declarative defs (`[forTableColumnDef]`, `[forTableRowDef]`, `[forTableColumnDragPlaceholder]`, `[forTablePlaceholderCellDefault]`) discover their registry through DI at construction instead of being content-queried, which is what makes a **preset column component** expressible (the def lives in the preset's own view, and a view is never content). Element DI follows the declaration tree, so the second shape — a **scaffold wrapper** whose consumers project defs through `<ng-content>` — cannot work at all unless the wrapper can provide a registry on its own host and hand it to the body it owns. That is the same reachability argument that keeps the `_GROUP` registries public and moved `registerAnchor` back onto Select / Combobox, and it stops at reachability: what `forty-cdk/table` exports is the token, a `ForTableDefRegistry` **read** interface (`columnNames`), and `provideForTableDefRegistry()`. The eight `register*` / `unregister*` pairs live on an unexported `TableDefRegistration` + `TABLE_DEF_REGISTRATION` (listed in `registration-surfaces.mjs`), the state is its own provider so `ForTableBody` implements neither interface (sanctioned shape #1 above), and the body rejects a `[defs]` value that is not the registry the provider helper installs — so the library still owns the only implementation and keeps refactoring the protocol freely. Unlike a `_GROUP` registry this one's **resolver stays hidden**: the orphan error it throws is for piece authors, and a wrapper reads its own provider with a plain `inject(FOR_TABLE_DEF_REGISTRY)`, so the exported token is not left half-usable. Read an issue asking for a "registration API to be exported" this way — publish the reachability, keep the protocol.

The **tab-stop read-backs** are the other members the rule's "read-backs that exist only to serve them" clause reaches, and they stayed public deliberately: `ForRadioGroupContext.hasSelectedRadio` / `isFirstEnabledRadio`, `ForTabsContext.hasSelectedTrigger` / `isFirstEnabledTrigger`, and `ForCarouselContext.hasCurrentIndicator` / `isFirstEnabledIndicator` all answer "does this item own the group's single tab stop?", which is exactly the question a consumer's hand-written item piece has to answer to participate in the roving group at all. They are typed with `HTMLElement` / `boolean` only, so none of them surfaces a name the consumer cannot import. `[forAccordionItem]`'s `adoptTriggerId` / `adoptContentId` stay for the same reason plus one more: they are not registry membership but the library-wide static-id adoption seam (the `adopt…Id(el)` shape documented above), with a signature shared by every primitive whose id lives on the context — hiding one primitive's would fork the seam without removing anything from the surface. `ForFieldsetContext.adoptLegendId` ([#1654](https://github.com/tutkli/forty-cdk/issues/1654)) is the second member of that set and was authored public for the same reason.

### A registered piece seeds `unsetInput`, never `input.required` ([#1601](https://github.com/tutkli/forty-cdk/issues/1601))

A piece registers with its parent from its **constructor**, during the content view's _creation_ pass, and has its bindings written in that view's _update_ pass. Any parent lookup that runs in between — a label-cache fold primed by a bridge effect, a virtualized navigator's position snapshot, an ARIA pairing resolved synchronously so the pre-hydration DOM carries it, a def registry read from a preset component's view whose two passes straddle the body's own render — reads an input the consumer has not supplied yet. `input.required` answers that read by **throwing** NG0950, which is why ten lookups across five entry points were once wrapped in a `try` / `catch` keyed on an Angular error code, with the exception used as control flow.

**So a mandatory input the parent may read early is declared optional and seeded with the sentinel instead:**

```ts
readonly value = input(unsetInput<T>());

constructor() {
  assertInputBound(this.value, 'listbox', '[forListboxOption]', 'value');
  // …register
}
```

The parent's lookup becomes an identity comparison (`isUnset(value)`), the piece is skipped for that run, and — because Angular's input signal registers itself as a producer _before_ it resolves a value — the read is still tracked, so the binding's write marks the reader dirty and folds the piece in on the run that follows. All three symbols live in `core/src/unset-input/`.

Five rules govern it, and each one is a bug that was live at some point:

- **Never `undefined` as the sentinel.** `ForListbox<T>` / `ForSelect<T>` / `ForCombobox<T>` are generic over an unconstrained `T`, so `undefined` is a legitimate consumer value and an `=== undefined` guard would silently drop such an option from the snapshot — an out-of-band sentinel swapped for an in-band one. A module-private `unique symbol` cannot collide with anything.
- **`unsetInput<T>()` casts to the input's own `T`, so the compiler will not help you.** That cast is the one place the library lies about an input's type, and it is deliberately confined to that function: nothing downstream widens to `T | undefined`, and in exchange every read site must guard by hand. Grepping `unsetInput` is the complete ledger of pieces on this shape; do not keep a roster here, it rots.
- **Guard before the value leaves the read site, and mind the read order.** A convenience destructure (`const { id, value, label } = …`) leaks the sentinel: `ForComboboxOption`'s label resolution calls the consumer's `itemToStringLabel` for a non-string value, so every fold reads `value` first and `continue`s before it touches `label`. The same care applies to the three options' `selected` computeds (they call `compareWith`) and to any lookup handing the value to a consumer callback.
- **Write channels guard too, not just folds.** Activation commits the value to `[(value)]` and hands it to `compareWith` / `toggleInArray`, so `activate` / `commitOnTab` on each root and every `RangeSelectionEngine` action bail on the sentinel. Otherwise a piece that is never bound corrupts the value model instead of failing.
- **`assertInputBound` is the replacement for the lost compile-time error, and it only covers dev.** Seeding the sentinel makes the input optional to the template type checker _and_ to Angular's `hostDirectives` required-input validation, so both channels that used to reject a missing binding now accept it. The assert runs in an `isDevMode()`-gated `effect` — a production build creates no reactive node per piece — and, because it is a view effect running inside `refreshView`, a throw **aborts the render** rather than degrading to a reported error. That makes dev loud; production has no net, which is why the guards above are load-bearing rather than defensive.

### The core tier — blessed vs internal ([#1398](https://github.com/tutkli/forty-cdk/issues/1398))

`forty-cdk/core` is a ~220-symbol barrel where consumer-grade contracts (`WritingDirection`, `VetoableEvent`, `DateAdapter`) sit next to the engines the library refactors freely (`MenuOverlay`, `OverlayManagerCore`, `DateFieldEngine`, `RangeFieldComposer`, the drag-session suite). A barrel can only promise semver all-or-nothing, so the promise is made **per symbol** instead, and the boundary is mechanical:

- **Blessed** — the curated set in [`scripts/lib/core-blessed-tier.mjs`](../../scripts/lib/core-blessed-tier.mjs), keyed by the entry point that **publishes** each symbol (`CORE_PUBLISHERS`; `BLESSED_CORE_SYMBOLS` is derived from it, so a symbol cannot be blessed without a canonical import path). These carry the library's semver guarantee and are the only core symbols allowed to appear in a public entry point's public signature.
- **Internal** — everything else in the barrel, by omission. No semver guarantee; refactorable without notice. It stays exported because the primitive entry points import it by the `forty-cdk/core` specifier, which is what keeps the DI singletons single-instance (see the barrel header) — exported is not the same as public.

**The marker is the curated list, not an `@internal` JSDoc tag.** `stripInternal: true` in [tsconfig.lib.prod.json](../../projects/forty-cdk/tsconfig.lib.prod.json) erases `@internal`-tagged declarations from the emitted `.d.ts`, and 30+ public directives `extends` a core base (`FormUiControlBase`, `ModalSurfaceBase`, `MenuOverlayHost`, `AnchoredOverlayPositioningBase`, `ForDateTimeSegmentBase`, `TextValueControlBase`). Tagging those would delete the base from `forty-cdk-core.d.ts` and leave every subclass in the shipped types extending a symbol that no longer resolves — a consumer-side typecheck break. Never tag a core symbol `@internal` to demote it; add or omit it from the list instead.

**Class bases reachable only through `extends` are internal on purpose.** They appear in the shipped `.d.ts` as the base of a public class, but subclassing a library base is not a supported contract, and `check-entrypoint-public-types.mjs` deliberately ignores `extends`-only heritage (it inspects `implements`, parameters, properties, and type arguments). Do not bless a base just because it is visible.

`scripts/check-entrypoint-public-types.mjs` runs in `postbuild` and enforces five things:

1. **The list cannot rot** — every blessed name must still be exported from `core/src/public-api.ts`, and no symbol may be assigned to two publishers. Renaming or dropping a blessed symbol fails the build, so the tier can never silently point at nothing.
2. **No internal-tier leak** — an internal core symbol fails the build when it appears in an entry point's public signature **or** as a re-export from its barrel. Both channels matter: a barrel re-export publishes the symbol just as effectively as a signature does, and it is the channel [#1140](https://github.com/tutkli/forty-cdk/issues/1140) / [#1180](https://github.com/tutkli/forty-cdk/issues/1180) opened. A stable barrel can only re-export blessed symbols, so demoting a symbol that already leaked is impossible to do by accident. Note the check reads the **built** `.d.ts`, so it sees re-exports routed through an intermediate module (`drawer/drawer-context.ts` re-exporting `ForDrawerSide`) exactly as ng-packagr flattens them — a source-level grep of the barrels does not.
3. **No duplicate import path** — re-exporting a blessed symbol from an entry point that is not its publisher fails the build. This is what keeps the retired per-barrel re-exports from growing back one convenient `export type { WritingDirection } from 'forty-cdk/core';` at a time. `export * from 'forty-cdk/core'` fails outright in any entry point: it publishes the whole internal tier and cannot be audited per symbol.
4. **The canonical path cannot vanish** — every symbol `CORE_PUBLISHERS` assigns to an entry point must actually be re-exported from that entry point's built `.d.ts`. Deleting the re-export without moving the symbol fails the build, so a blessed symbol can never become unreachable.
5. **No unnameable public type** — a type declared in the entry point's **own** sources fails the build when a public exported signature surfaces it and the barrel does not export it ([#1345](https://github.com/tutkli/forty-cdk/issues/1345)). Rules 2–4 only ever saw types imported from `forty-cdk/core`, so this channel was invisible to every gate: nothing is out of tier, the name is simply unreachable, and the consumer is silently pushed onto structural typing. Detection walks the same public signature as rule 2 (`implements`, parameters, properties, type arguments; `extends`-only bases and `protected` / `private` members excluded) rooted at the barrel's exports, then follows the leaks transitively — a type reached only through another unexported local is equally unnameable, which is how `MenubarMenuHost` and `MenubarPositioningSeeds` surface behind `ForMenubar.menuCtx`. The known instances are listed per entry point in [`scripts/lib/unnameable-public-types.mjs`](../../scripts/lib/unnameable-public-types.mjs), and the gate fails just as loudly when a listed name stops leaking, so that list cannot rot either.

**To bless a symbol** (a deliberate, reviewed act — it is a permanent semver commitment): add its exported name under the entry point that will publish it in `CORE_PUBLISHERS` — `shared` unless the symbol's semantic home genuinely is one primitive — re-export it from that entry point's barrel, and confirm the JSDoc reads as consumer-facing documentation rather than an implementation note. Prefer the alternative first — narrow the leak so the symbol never crosses the boundary. Blessing is right when the symbol is genuinely part of a supported contract (a context interface an advanced consumer injects, a value-set a public input accepts); it is wrong as a shortcut to make the gate quiet.

**A locally-declared leak has the same two resolutions as a core one — narrow it, or publish it — and retyping is the first thing to try.** The leak is often just a second spelling of something already blessed, which makes it the defect the paragraph below describes rather than a missing export: `[forDatePicker]`'s `granularity` input was typed with a module-local `DatePickerGranularity` byte-identical to the blessed `FieldGranularity`, so it was retyped rather than given a public name of its own. Publishing is right when the type is a genuine part of the contract and has no blessed twin — `TailwindBreakpointName` (the fallback union behind the exported `BreakpointName`) and `BuildTimeSlotsConfig` (the parameter of the exported `buildTimeSlots`) were both simply added to their barrels. The six names deferred in the list today are two groups, and each has a reason the two resolutions do not reach yet. The nine **registration handles** that used to be a third group (`ForAccordionTriggerHandle`, the three `ForCarousel*Handle`, `ForRadioHandle`, the two `ForTabs*Handle`, the two `ForToast*Handle`) left the list with the #1399 split that removed the `register*` members surfacing them ([#1524](https://github.com/tutkli/forty-cdk/issues/1524)) — never by a re-export, which is the opposite of what that split is for. They now live in `registration-surfaces.mjs` instead, so the guarantee is stronger than a deferral: the gate fails if one becomes public again. Because this gate fails on a stale entry too, the removal and the `registration-surfaces.mjs` addition had to land in the same commit.

- **Overlay-manager entry shapes** (`ForDialogEntry`, `ForDrawerEntry`) — reached only as the type argument of an `extends OverlayManagerCore<…>` clause. The base is internal on purpose per the rule above, so the argument names an entry the consumer never constructs; the leak is real (the inherited members typed with it are public) but resolving it means deciding what a manager's entry list is worth as a contract, which is not this gate's call.
- **The menubar context implementation** (`MenubarMenuContext` + the two shapes its constructor takes) — `ForMenubar.menuCtx` cannot simply become `protected`, because the root's own `FOR_MENU_CONTEXT` provider reads it through a `useFactory`, which TypeScript checks as an access from outside the class body.

`ForTableRowContext` is the odd one out and stays on its own: it is published only by `ForTableRow`'s `implements` clause, and its token is deliberately absent from the barrel — so a consumer can see the name of a surface they cannot inject.

Do not give a blessed symbol a second public name. `SegmentType` used to reach consumers aliased as `DateTimeSegmentType` from `forty-cdk/date-field` / the then-separate `forty-cdk/date-range-field`; #1486 dropped the alias, because a second name is the same duplicate-path problem as a second specifier. The rule holds one level down too: a second _internal_ name for a blessed symbol is the same defect. `core/menu-overlay` carried `MenuOverlayCloseReason`, a byte-identical copy of the blessed `ForMenuCloseReason`, and `MenuOverlayItemHandle`, a bare alias of `MenuItemHandle`; [#1400](https://github.com/tutkli/forty-cdk/issues/1400) deleted both rather than let the engine spell a published contract under a private name.

### A type or member reachable from a public signature is never `@internal` ([#1630](https://github.com/tutkli/forty-cdk/issues/1630))

The tier rule above — never tag a **core** symbol `@internal` to demote it — generalizes to every entry point, and the reason is that `stripInternal` deletes the tagged declaration while leaving every reference to it in place. That is the one leak the five rules structurally cannot see: both of rule 5's branches need the referenced name to resolve to _something_ in the emitted file, and a stripped declaration resolves to nothing. Two shapes have shipped. A **dangling type reference** — `FOR_TOAST_DEFAULTS: InjectionToken<ResolvedToastDefaults>` with `ResolvedToastDefaults` declared nowhere in `forty-cdk-toast.d.ts` (`TS2304`), live for three releases until [#1629](https://github.com/tutkli/forty-cdk/pull/1629) folded that shape into the public `ForToastDefaults`. And a **class that no longer satisfies its own `implements` clause** — `ForAvatar.reportStatus` tagged `@internal` while the `ForAvatarContext.reportStatus` it implements was not, so the emitted class lost the member and the interface kept it (`TS2420`), live on `main` until #1630 dropped the tag. Both are invisible to almost everyone, since `skipLibCheck` defaults to `true` in every Angular CLI application, and total for the consumer who does verify their dependencies' types: the error is in a file they cannot edit.

Those two shapes are not a coincidence, and knowing why bounds what the gate is for. A stripped symbol that **another module imports by name** fails ng-packagr's own DTS bundler during `pnpm build` (`"X" is not exported by …, imported by …`), before any postbuild gate runs — so that half was never silent. What survives the emit is the reference no import ever names: a type **declared and referenced in the same source file** (`ResolvedToastDefaults` beside its token), and a **member**, which no module imports by definition. Tagging a core base `@internal` is caught by the bundler too, because `core/src/public-api.ts` re-exports it by name — so the hazard the tier paragraph warns about stands on its own merits rather than on this gate.

`scripts/check-emitted-types-compile.mjs` (`postbuild`, ~3 s) closes the hole by typechecking `dist/forty-cdk/types/*.d.ts` with the compiler itself under `strict` + `skipLibCheck: false`, failing on any diagnostic. Spending a `tsc` pass rather than extending the AST walk is the deliberate half of that: the walk would need a hand-maintained allowlist of every name that legitimately resolves without a local declaration (lib globals, the `_angular_core`-qualified ones it already handles), which is the kind of list this gate family exists to avoid — and the compiler catches malformed emit beyond an unresolved name. Module resolution is the consumer's too: the emitted files import each other by published specifier (`forty-cdk/core`), which resolves through the package's own `exports` map by Node's self-name rule, so a missing or misrouted export condition fails here as well. **It runs first of the nine**, because "does the emit compile at all" precedes every question about the shape of its surface, and because a stripped declaration makes rule 5 report the _opposite_ of the truth: the leaked name stops resolving, so that gate sees a deferral whose leak is gone and asks for the name to be dropped from `unnameable-public-types.mjs`. Reading that message before the compiler's is how an author talks themselves into deleting the tracking for a break they just shipped.

**The gate carries a liveness probe, because its whole detection power lives in five compiler options and one of them can switch the check off without switching it red.** A refusal to run on an empty `types/` covers the obvious vacuum; it says nothing about a run that compiles 350 files and has been made incapable of reporting on any of them. `skipLibCheck: true` is that switch — it suppresses semantic checking of _every_ `.d.ts`, the emitted ones included, which is the same property that let the toast break ship in the first place — so the probe is a synthetic declaration file compiled alongside the emit, carrying one instance of each shape above: a dangling type reference and a class that does not satisfy its `implements` clause. A green run must report both, named by code (`TS2304` + `TS2420`) in the OK line, and a run where either goes missing fails with "this run proves nothing about the emit" instead of passing. It is a module (it exports), so its names never reach the global scope the emitted files share, and it costs nothing measurable — one more file in a 352-file program. **The answer to a probe failure is to restore the detection, never the probe.**

The resolutions are the same two as for any other leak: **narrow** the signature so it stops reaching the tagged thing, or **drop the tag and publish it**. Both instances above took the second, which is usually the honest one — the tag was hiding a shape a public signature had been describing all along (`ForAvatarContext` published `reportStatus` either way; the tag only made the emitted class disagree with it). Narrowing avatar properly meant taking `reportStatus` off the public context, which is what [#1722](https://github.com/tutkli/forty-cdk/issues/1722)'s inverted default did: it now lives on the unexported `AvatarPieceContext`, `ForAvatar` declares it `private`, and the emitted class and interface agree without a tag. That is the general shape — **a member you want to write "consumers should not call this" about is a member on the wrong interface**, and `@internal` is never the fix.

## Entry-point granularity — when a primitive earns its own secondary entry point

Every folder under `projects/forty-cdk/` carrying an `ng-package.json` becomes a published import specifier, and the library has 60 of them. There was no written rule for when to add one, which is how the layout came to contradict itself. The rule:

**A primitive earns its own secondary entry point when it satisfies at least one of three clauses.**

1. **It isolates an optional or heavy dependency.** `forty-cdk/internationalized-date` exists so only consumers of the `@internationalized/date` adapters need that peer installed; `forty-cdk/virtualization` isolates `@tanstack/virtual-core`. This is the strongest clause — it is the only one where merging would _break_ a consumer's build rather than merely coarsen a chunk.
2. **It implements an independent WAI-ARIA APG pattern.** One pattern, one entry point: `forty-cdk/listbox`, `forty-cdk/dialog`, `forty-cdk/tabs`. A composition that reuses another pattern's backbone still counts when it is a distinct pattern (Stepper reuses the Tabs backbone and is its own entry).
3. **It is a standalone headless composable belonging to no primitive's anatomy.** `forty-cdk/breakpoints` (`injectBreakpoints`) is the one: no role, no DOM, no APG pattern, and no primitive whose anatomy it is part of. It is its own entry because the alternative is arbitrary — folding a composable into an unrelated primitive's entry makes that entry's name stop describing its contents. `forty-cdk/signal-forms` (`forSingleValueField`) was the second until [#1579](https://github.com/tutkli/forty-cdk/issues/1579) retired its only export; see the recorded decision below.

**A _variant_ of a primitive ships inside its base's entry point.** A variant is a second root over the same APG pattern and the same pieces — a range picker next to a single picker, a multi-value flavour of a single-value control. It gets no entry of its own, because per-entry-point isolation buys nothing there: within one entry's FESM the unused root is a standalone class under `"sideEffects": false`, so a consumer who never imports it never bundles it. What an extra entry point _does_ cost is fixed and paid at authoring time — six registration lists (root `tsconfig.json` paths, `projects/forty-cdk/tsconfig.{lib,spec}.json`, the harness and playground `tsconfig.app.json`, `angular.json`'s test `include`, all enforced by `scripts/check-entrypoint-registration.mjs`) plus an `ng-package.json`, a README, and an SSR fixture. Pay it for a real boundary, not for a naming preference.

**Recorded decision — the range fields are folded, so the rule now ships with no counter-example ([#1716](https://github.com/tutkli/forty-cdk/issues/1716)).** `ForDateRangeField` and `ForTimeRangeField` shipped as `forty-cdk/date-range-field` / `forty-cdk/time-range-field` for as long as this rule existed, and the paragraph that used to sit here recorded them as "the known deviation" scheduled with the next pre-1.0 breaking batch ([#1401](https://github.com/tutkli/forty-cdk/issues/1401) item 5). Both specifiers are gone: every symbol is exported from `forty-cdk/date-field` / `forty-cdk/time-field`, exactly where `ForDateRangePicker` sits inside `forty-cdk/date-picker`. Three things the fold established:

- **The fold bought no deduplication, and expecting it to is what made it look bigger than it was.** Unlike [#1589](https://github.com/tutkli/forty-cdk/issues/1589) there was no cross-entry-point import edge to remove, and unlike `ForDateRangePicker` — which literally shares `date-picker-base.ts` with `ForDatePicker` — there was no shared file. Neither range root imported its base entry point; both reach the shared machinery through `forty-cdk/core` (`DateFieldEngine`, `FormUiControlBase`, `injectHiddenInput`, `injectTextDirection`), and the range roots add `RangeFieldComposer` on top. Not one import inside the four roots changed. **The payoff is that the rule above no longer has to be read past a standing exception**, which is the whole of what a packaging rule is worth.
- **The recurring cost was per-entry-point and it is what the ledger under-counted.** Six registration lists × 2 is the visible half; the rest is the SSR and static-adoption sweep fixtures, two cross-primitive contract specs, two harness fixtures + routes + E2E suites, and four playground surfaces per entry (demo folder, route, `primitives.ts`, two generated files). A grep over `*.json` sees six files and lies about the size.
- **A variant's docs and demos fold with it, because the doc surfaces are keyed by entry-point folder.** `scripts/gen-search-index.mjs` indexes `projects/forty-cdk/<entry>/README.md`, and a playground page renders the README of the entry whose slug it carries — so a variant keeping its own page after the fold would have had to render its base's README. Each range README is now a `## Range selection — For<X>RangeField` section of its base's, and the demos are `range*.example.ts` in the base's demo folder, which is the shape `date-picker` already had.

Cite this decision, not the old deviation, when a new variant asks for an entry point of its own.

**Recorded decision — a cross-primitive adapter gets its own entry point, one per isolated primitive ([#1589](https://github.com/tutkli/forty-cdk/issues/1589)).** `forty-cdk/virtualization` exists under clause 1, to isolate `@tanstack/virtual-core` — and it used to import two other primitives on top: `[forTableVirtualized]` pulled `forty-cdk/table` and `[forVirtualReorder]` pulled `forty-cdk/drag-drop`, so a consumer who wanted nothing but `injectVirtualizer` for a plain list got an entry point whose FESM top-level-imported both. The two adapters now ship as **`forty-cdk/table-virtualization`** and **`forty-cdk/virtual-reorder`**, and the entry point they left contains only the windowing core, the Shape A viewport pair and infinite-scroll — `@tanstack/virtual-core` is its one third-party dependency, and `forty-cdk/core` (`afterNextRenderCancellable`, the sanctioned internal tier every primitive imports) its only remaining entry-point edge. It imports no other primitive. Four things about that decision are worth keeping, because each one is a repair that looks right and is not:

- **The issue's own alternative — keep the placement and add a bundle probe — cannot be built cheaply, and would prove the wrong property if it were.** A probe has to run the **Angular CLI's optimizer**, not a bare `esbuild` pass: ng-packagr's FESM declares each directive as a class with a static `ɵɵdefineDirective` initializer, which is a side effect to any bundler, and `@angular/build`'s `/*@__PURE__*/` annotation pass is what makes those classes droppable. Measured on this repo at the time of the split, bare esbuild over `dist/` retained the table and drag-drop FESMs **byte-identically** whether the entry imported `injectVirtualizer` alone or both adapters — a probe written that way reports a catastrophe that is not happening, and one written with a scratch `ng build` costs a second Angular compilation in `postbuild`. And a green probe would only ever have proven **tree-shaking**, whereas the property the layout is built on is **chunk granularity**: [#1046](https://github.com/tutkli/forty-cdk/issues/1046) measured a real consumer app pulling one 356 KB forty chunk eagerly off a ~15 KB touch, with tree-shaking working correctly the whole time. A static import edge between two entry points is exactly what merges their chunks.
- **One adapter, one new entry point — the issue proposed a single `forty-cdk/table-virtualization` holding both, and that reproduces the defect one level down.** `[forVirtualReorder]` is not a table thing (it is the drag-drop-side analogue of `[forTableRowReorder]` for plain windowed lists), so a consumer importing it out of a table-named entry would pull `forty-cdk/table` for a list that has no table in it — and the entry's name would stop describing its contents, the same failure the `signal-forms` decision below turns on. The rule generalizes: an adapter entry point isolates **one** primitive beyond its own base, and a second adapter over a second primitive earns a second entry.
- **The direction of the remaining edges is still load-bearing.** Both new entry points import `forty-cdk/virtualization`, and `[forTableVirtualized]` additionally imports `forty-cdk/table` — that is what an adapter is. What must not come back is an edge **out of** a base entry point: `forty-cdk/table` still never imports `forty-cdk/virtualization` (the additive `registerVirtualWindow` seam on the internal registration surface is what buys that, see the `<for-table-body>` entry in the exceptions list below), and `forty-cdk/virtualization` now imports no primitive at all.
- **A future virtualized adapter lands in its own entry point too.** `[forTreeVirtualized]` / `[forListboxVirtualized]` would each isolate one more primitive; adding them to `forty-cdk/virtualization` is what this decision exists to prevent, and adding them to `forty-cdk/table-virtualization` would be the naming lie above.

**Recorded decision — `forty-cdk/signal-forms` is retired, not folded ([#1579](https://github.com/tutkli/forty-cdk/issues/1579)).** The entry point existed for one export, `forSingleValueField`, which adapted a `FieldTree<T | null>` into the `FieldTree<readonly T[]>` view the selection controls accept. That adapter is gone and the specifier with it — an earlier decision to keep the entry (over folding it into `forty-cdk/field`) was about where the export lived, and became moot once the export itself did not survive. Folding was reconsidered and rejected for the same reason it always was: `forty-cdk/field` is the `[forField]` label / description / error wiring composition, and re-homing a deleted symbol's entry point there would leave a name that stops describing its contents.

**What replaced it is a shape rule, not a second helper: a single-select form field is modeled as the same `readonly T[]` the control exposes, kept at length ≤ 1, and bound with `[formField]` directly.** Three things make that the only shipped answer, and each one is a reason not to reopen the adapter:

- **Angular's template type-checker adds a two-way `[value]` binding between the field and _every_ directive on the host that owns a `value` model** (`getCustomFieldDirectiveType` is evaluated per directive, not for one winner), so the field's value type must line up with the root's in both directions. A `readonly T[] | T | null` union model fails the write half; a second, single-valued adapter directive alongside the root fails because the root is still type-checked against the same field. At runtime `initializeCustomControlStatus` resolves the channel in two passes: the **first selector-matched** directive with a `value` model wins outright, and only when none has one does Angular fall back to a model exposed through `hostDirectives` (a non-range host directive never enters `tNode.directiveToIndex`, so the first pass skips it). Composing an adapter onto the root therefore cannot take over the value channel _while the root itself declares `value` as a model_ — the first pass resolves before the host-directive pass is evaluated at all. Relocating the channel to a host directive would mean the three roots dropping their public `[(value)]`, a far larger break than the one taken here, so treat the two-pass order as the reason the composed adapter is dead rather than a blanket "host directives can't be controls". The only type-correct shape that keeps `[(value)]` is a wrapper that _replaces_ the root as the selector-matched directive — three new public directives re-exposing three full input/output surfaces, which is what this decision declined.
- **A mapped `FieldTree` view cannot be built without reflection.** Angular exposes no writable-computed primitive (`signal` / `linkedSignal` / `model` only), so a two-way mapped value signal means mutating a `computed` after creation; and `FieldTree<readonly T[]>` is `(() => FieldState<…>) & ReadonlyArrayLike<MaybeFieldTree<T, number>>`, so a faithful view also owes per-element subfield trees. The retired helper answered both with `as unknown as`, which is exactly why each bet would have failed silently on a dependency bump instead of at compile time.
- **The plain binding loses nothing.** `[formField]` writes `disabled` / `readonly` / `required` / `invalid` / `errors` / `touched` onto _any_ directive on the host declaring that input, and routes `focus()` through the control's own `focus()` — so the pass-through the adapter existed to preserve is what a direct bind already does. The executable record is [`src/lib/single-select-form-field.spec.ts`](../../projects/forty-cdk/src/lib/single-select-form-field.spec.ts), one parameterised contract over all three roots.

### Core module granularity — when a helper earns its own `core/` directory ([#1592](https://github.com/tutkli/forty-cdk/issues/1592))

The same question one level down, and until this pass it had the same answer the entry-point one used to have: none. `core/src/` reached **64 directories over 208 files, 114 of them source** — forty-nine of them holding a single source file, twenty-two exporting a single symbol to the barrel — because every split was locally defensible and nothing said when to stop. The cost is not correctness, it is that a contributor cannot hold the surface in their head, so the failure mode is a _duplicate_ helper. The rule:

**A helper earns its own `core/` directory when it is a concern a contributor would look for by name rather than a facet of one that already exists — in practice, when it spans more than one file or its consumers do not share a single owning concern. Otherwise it is a file inside the directory whose concern it serves.**

Six things the consolidation down to 43 directories established, each of which is a wrong turn worth not retaking — and one thing it deliberately did not do: **21 of the 43 still hold a single source file.** The rule is a disjunction, so those rest entirely on its second clause (their consumers share no owning concern), which no scan can check. Read that as the state of play rather than as a backlog: a further pass would be judgement about concerns, not arithmetic about files.

- **A merge does not shrink the barrel, and expecting it to is what makes the pass look unfinished.** Merging directories moves files; the exported names travel with them. Of the barrel's 229 symbols, 219 were imported by non-spec code in at least one entry point, four more only by a spec in another entry point, and the remaining six are named by an emitted signature (the barrel header's own carve-out), so the reachable reduction was **one** — `clampToRange`, a redundant second name for `clamp`, which is the [#1400](https://github.com/tutkli/forty-cdk/issues/1400) duplicate-name defect rather than a granularity one. The metrics a merge moves are directories and files; measure the census before promising a symbol count.
- **A mutual import between two directories is the strongest merge signal there is**, because it says the boundary is not one. `scroll-boundary` and `swipe-dismiss` each imported the other; so did `date-adapter` and `datetime` in effect, since `datetime` was the adapter's only intra-core reader. Read the intra-core edges before reading the file names — including after you have chosen, because an edge also falsifies a placement. This pass first left the two hover predicates in `hover-intent/pointer-capability.ts` and then created a `pointer/` directory whose whole justification is "what is the pointer really doing"; the tell was `pointer/pointer-grace.ts` importing them across the boundary, and `button/hovered.ts` consuming `isNonTouchPointer` while being no part of the hover-intent family. They live in `pointer/` now.
- **A helper that does not earn a directory earns a _file_, not a paragraph inside somebody else's.** The distinction is the whole of the rule's second sentence and it is easy to lose, because the issue that asked for this pass counted files: `createDebouncedAction` was folded into `hover-intent.ts` to reach a file target, which put a generic debounce timer — whose three consumers are `[forMenuSub]`, `[forNavigationMenu]` and `[forContextMenuTrigger]`'s **long-press**, none of them hover-intent and none of them `createHoverIntent` — inside a file named after a family it does not belong to. It is `hover-intent/debounced-action.ts` again: same directory, same 43-directory count, name restored. Merge to the directory; let the directory hold as many files as it has concerns.
- **"One entry point consumes it" is [#1490](https://github.com/tutkli/forty-cdk/issues/1490)'s question, not this one.** That issue relocates a single-consumer module _out_ of core; this one decides whether what stays is one directory or six. A module two entry points import stays in core no matter how small — `window-index-map` is 95 lines with two functions and both `forty-cdk/table` and `forty-cdk/virtual-reorder` call them, so it became `drag-session/window-index-map.ts` rather than moving anywhere.
- **A `core/` directory name is internal, so renaming one costs only the prose that names it** — this file, the `source:` paths in [`static-adoption/fixtures/`](../../projects/forty-cdk/src/lib/static-adoption/fixtures/), and the `<file>::<member>` trackers in [`roving-tabindex-adopters.spec.ts`](../../projects/forty-cdk/src/lib/roving-tabindex-adopters.spec.ts) are the only path-keyed references in the repo. Every gate keys on symbol names, every entry point imports through the `forty-cdk/core` specifier, and the generated matrices below re-key themselves from source. Rename the absorbing directory when the merged contents outgrow its name (`host-aria` → `host-attributes` for the four host seams, `pointer-grace` → `pointer`); keep it when they do not.

### The root barrel exports nothing, deliberately ([#1590](https://github.com/tutkli/forty-cdk/issues/1590))

[`projects/forty-cdk/src/public-api.ts`](../../projects/forty-cdk/src/public-api.ts) is `export {}`, so `import { … } from 'forty-cdk'` resolves to no symbol and editor auto-import finds nothing under the package name. That is the decision, not an oversight: the specifiers are `forty-cdk/<primitive>` for every primitive and `forty-cdk/shared` for the blessed tier. Do not populate the root barrel, and do not treat the empty file as a gap to fill on the way past.

**The repair everyone reaches for first — publish the blessed tier from the root — reintroduces the duplicate import path [#1486](https://github.com/tutkli/forty-cdk/issues/1486) was opened to remove.** `forty-cdk/shared` has shipped since [#1488](https://github.com/tutkli/forty-cdk/pull/1488), so its 42 symbols cannot _move_ to the root without breaking every consumer already importing them; the root would be an **alias** (`forty-cdk` ≡ `forty-cdk/shared`), and the `CORE_PUBLISHERS` entry it needs is an explicit exception to the one-publisher-per-symbol invariant rather than a way of satisfying it. Rule 3 and the duplicate-publisher check in `check-entrypoint-public-types.mjs` reject it by construction — which is the gate working, not a gate to carve out.

Three further properties, the first two of which also settle the narrower "types only" variant:

- **Re-exporting the types only leaves the surface asymmetric.** The [`shared` barrel](../../projects/forty-cdk/shared/src/public-api.ts) is 34 `export type` plus 8 runtime values (`accessibleTextContent`, `assertTimeCapable`, `FOR_DATE_ADAPTER`, `FOR_FIELDSET_CONTEXT`, `FOR_ID_SALT`, `FOR_MENU_CONTEXT`, `injectDateAdapter`, `provideForIdSalt`), so `import type { DateAdapter } from 'forty-cdk'` would resolve while `import { injectDateAdapter } from 'forty-cdk'` would not — 34 of the 48 blessed symbols offered by the editor, failing on the 8 that are values, with no message explaining the split.
- **No variant reaches the six symbols a primitive publishes.** `ForVisuallyHidden`, `ForDrawerSide` and the field-wiring quartet have a primitive as their semantic home, so the root would not be "where the blessed tier lives" under any of them.
- **The discovery cost is real and none of this pays it down.** Someone typing `forty-cdk` and waiting for a suggestion wants `ForDialog` / `ForAccordion`, and putting the primitives in the root barrel is ruled out by the per-entry-point isolation the whole layout exists for. Publishing 42 shared contracts there would make the root look populated without answering that first search.

The gate needs nothing: `forty-cdk.d.ts` stays in `IGNORED_FILES` ([check-entrypoint-public-types.mjs](../../scripts/check-entrypoint-public-types.mjs)) because the file it would audit has nothing in it. Note that a populated root barrel would also have to be checked against [#1345](https://github.com/tutkli/forty-cdk/issues/1345)'s use of a flattened `.d.ts`'s trailing `export {}` as a signal — one more reason the empty file is the cheap answer. The consumer-facing half of this policy is the _Entry points_ section of the [package README](../../projects/forty-cdk/README.md).

## Cross-primitive conventions

These keep the surface predictable across primitives. Apply them everywhere; deviate only with a written reason.

**`data-state` vocabulary.** Three canonical families, picked semantically — never invent a fourth without listing it in the _Documented alternative vocabularies_ table below:

- `"open" | "closed"` — for things that expand/collapse (`Disclosure`, `Accordion`, `Tooltip`, `Dialog`, `Tree` parent items, future `Popover`/`Menu`/`Drawer`).
- `"active" | "inactive"` — for one-of-N selectables embedded in a tablist-like container (`Tabs` trigger and content).
- `"checked" | "unchecked" | "indeterminate"` — for form-control state (`Switch`, `Checkbox`, `RadioGroup` items, `Listbox` options, future `Select`/`ToggleGroup`). `"indeterminate"` only on tri-state controls (Checkbox today).

`data-state` is reflected on every piece of the primitive that the consumer might want to style — the root _and_ trigger/content/option/etc. — using the same vocabulary across pieces.

**Documented alternative vocabularies.** A handful of primitives intentionally use a different attribute name or value set because the underlying spec / pattern doesn't fit any of the three families above. **Boolean `data-*` attributes.** Present (with empty string value) when `true`, absent (`null`) when `false`. Never emit `data-disabled="false"`. **The spec-side guard for both rules above is `assertDataStateContract`** ([#1597](https://github.com/tutkli/forty-cdk/issues/1597), `src/test-utils/contract/`): a piece declares the value set it emits, and the contract asserts the declaration is one of the families above, that every piece of the primitive reflects the same value in the same state, and that no `data-*` attribute on any of them ever carries the literal `"false"`. Adoption is not a roster — `src/lib/data-state-adopters.spec.ts` derives the emitting entry points from source with the same extraction that generates the `data-state` matrix rows below, so a new vocabulary must satisfy `pnpm check:matrices` **and** the contract's family list. Its scope is a `data-state` bound to a **literal** value set; a value set living in a signal or method's type is outside both (see `.claude/rules/testing.md`).

**`[id]` host bindings adopt a consumer-set _static_ id ([#659](https://github.com/tutkli/forty-cdk/issues/659)).** Every piece that host-binds `[id]` for aria wiring (overlay trigger / content, options, group labels, titles / descriptions, headings, tab triggers / panels, …) must preserve a consumer-set **static** `id` rather than clobbering it with the generated fallback — a consumer's `id` is the anchor for external `aria-labelledby` / `aria-describedby` references, label `for`, and test hooks. The mechanism is the shared `core/host-attributes/host-id` helper:

- **Piece owns its id** (was `readonly id = signal(idGen.next('…'))` host-bound `[id]='id()'`): use `readonly id = hostId('for-<primitive>-<piece>')`. It seeds the signal from the host's pre-existing static `id`, else generates.
- **Id lives on the context / root** (trigger / content reading `ctx.triggerId()` etc.): the root seeds a generated id at construction, then adopts via `adoptHostId(el, idSignal)` — either inside the existing `register…(el)` method, or via a dedicated `adopt…Id(el)` method the piece calls from its constructor. Adoption MUST run synchronously at the piece's construction (before the first host-binding pass): once `[id]` writes, `el.getAttribute('id')` returns the generated value, not the consumer's static one.
- **`registerA11yName` / `registerA11yDescription`** already adopt the host's static id (they read `ElementRef` optionally), so title / description / group-label pieces need no per-piece change.

**Only _static_ ids are preserved — never property bindings.** A consumer `[id]="expr"` property binding evaluates _after_ directive construction, so it is invisible to adoption and still fights the `[id]` host binding (unpredictable last-writer). The supported contract is a plain `id="…"` attribute; document this boundary on any new piece. The library-wide guarantee is enforced by `assertStaticAdoptionContract` (`src/test-utils/contract/`), swept over the adopter registry in `projects/forty-cdk/src/lib/static-adoption/`, and its coverage is derived from source rather than declared: `adopters.spec.ts` fails on a call site of any of the six seams (`hostId` / `resolveHostId` / `adoptHostId` / `hostAriaLabel` / `hostLabelledBy` / `hostDescribedBy`) that no claim covers, and on a claim naming a call site that no longer exists.

**Adoption is also what makes generated ids survive hydration — which is why incremental hydration breaks exactly where adoption cannot run ([#1582](https://github.com/tutkli/forty-cdk/issues/1582)).** Nothing about a monotonic counter guarantees a server render and its client hydration agree; two properties do, and both were unstated until #1582 measured them. First, a hydrating piece reads its host's existing `id` — the one the server wrote — so `hostId` / `adoptHostId` re-emit the server's value even when the client counter has drifted. Second, every piece **outside** all `@defer` blocks mints before any dehydrated block hydrates on both sides: the server renders a deferred block's content _after_ the view containing it (so deferred pieces mint last), and the client hydrates no block until the initial pass completes. Level-0 ids are therefore byte-identical, and ordinary (non-incremental) hydration is exact everywhere.

The gap needs **both** halves: a root that is itself deferred (so its counter drifted) minting an id **for a piece that is still dehydrated** (so nothing adopts on that piece's behalf). The referring attribute then keeps the drifted counter's value and either resolves to nothing or — when the value collides with an id the server minted for an element in another dehydrated block — to the **wrong** element, permanently (each element keeps the id the server gave it, so hydrating the blocks does not heal it). Mind the second half when reading a report: a root at level 0 minting for a dehydrated piece is the split that _survives_, on the byte-identical guarantee above rather than on adoption, and the suite pins it as such — so the consumer-facing rule is conservative by choice, not because that shape was measured broken. Three consequences for a primitive author:

- **The supported rule is "one primitive, one hydration unit"** — documented for consumers under _Incremental hydration_ in the [`forty-cdk/shared` README](../../projects/forty-cdk/shared/README.md). Do not document a consumer static `id` as the hydration-safe path: it is the one shape that breaks even at level 0, where a generated id resolves, because the server adopts it and the client cannot. #1582 rejected that option (the issue's own suggestion (c)) on the evidence.
- **A new id-owning piece keeps the id on the context, adopted at construction.** Nothing about the shape needs to change for hydration — it is already the mechanism that makes hydration work — but a piece that mints an id and never adopts one would silently regress the level-0 guarantee above.
- **`aria-activedescendant` needs no rule and must keep it that way.** It resolves from a **registered** option handle, so it can only ever name a piece whose directive constructed (and therefore adopted); with the options dehydrated the attribute is absent rather than stale. A future activedescendant path that cached an id outside the handle registry would lose that.

The executable record is [`src/lib/ssr/incremental-hydration.spec.ts`](../../projects/forty-cdk/src/lib/ssr/incremental-hydration.spec.ts) — a real `platform-server` render driven through a real client hydration, not a simulation. See `.claude/rules/testing.md` for what that suite covers and why it cannot live in the SSR smoke suite.

**The same static-attribute adoption covers `aria-labelledby` and `aria-describedby` ([#1454](https://github.com/tutkli/forty-cdk/issues/1454)).** A host binding that resolves to `null` _removes_ the attribute, so **every** surface host-binding `[attr.aria-labelledby]` used to destroy a consumer-set static value — the ones emitting a generated trigger / heading id and the registry-driven ones alike (their `null`-when-nothing-registered branch removed it just as effectively). Two core helpers in `core/host-attributes/host-aria` own the semantics; never hand-roll a `getAttribute('aria-labelledby')` read in a primitive:

- **`hostLabelledBy(fallback)`** — the consumer's static value **replaces** the fallback. A name has one owner, and the consumer's is the one assistive tech should announce. Adopted by every `[attr.aria-labelledby]` host binding in the library: accordion content; the three calendar grids; combobox content / list / group; dialog + drawer (`ModalSurfaceBase`); fieldset; listbox group; menu content / group / radio group; navigation-menu content; popover content; select content / group; stepper content; tabs content; time-picker + date-picker content; toast.
- **`hostDescribedBy(fallback)`** — the consumer's static value is **composed** with the library's ids (consumer first, no duplicates), because descriptions are additive and assistive tech reads them all. Adopted by dialog + drawer, popover content, toast, and the tooltip trigger (whose open-gated tooltip id now appends to the consumer's hint instead of replacing it). Same composition `injectFieldWiring` applies to the control it targets — both call the shared `composeIds`.

The static-only boundary is identical to the `[id]` one: a `[attr.aria-labelledby]="expr"` binding is not adopted. No piece in the library exposes a reactive `labelledby` input; a name that already lives in the DOM is referenced with the native attribute, which the library never binds and therefore never erases.

**`aria-label` adopts the same way — through the third `core/host-attributes/host-aria` helper ([#1479](https://github.com/tutkli/forty-cdk/issues/1479)).** The mechanic is the one above with a larger blast radius: the canonical binding is truthy-only (`'ariaLabel() || null'`), so a consumer who names a widget with the native attribute instead of the `[ariaLabel]` input had it **removed** on the first render and the widget was left with no accessible name at all.

- **`hostAriaLabel(fallback)`** — the consumer's static value **replaces** the fallback, reusing `hostLabelledBy`'s semantics (a name has one owner). Adopted by every host whose accessible name is optional (`ariaLabel() || null`: the `Listbox` / `Menubar` / `NavigationMenu` / `Toolbar` / `Tree` / `Table` / `TabsList` / `StepperList` / `Pagination` / `Progress` / `Meter` / `Carousel` / `OtpInput` roots, the date & time fields and their endpoint groups, the calendar / carousel / pagination / number-input arrow buttons, the table row selectors, the slider thumb, `ModalSurfaceBase` for dialog + drawer) and by every host whose name is mandatory but **defaults-backed** (`[forBreadcrumbs]`, `[forComboboxChips]`, `[forComboboxClear]`, `[forSearchClear]`, `[forToastViewport]`) — there a static attribute is a per-instance override of the localizable default, exactly what `[ariaLabel]` already is. The ctx-driven overlay surfaces (combobox content / list, menu / popover / select / date-picker / time-picker content) adopt too. Never hand-roll a `getAttribute('aria-label')` read in a primitive.

  **There is no longer an un-migrated accessible name.** `[forToastViewport]` was the last one — its input was spelled `label` and defaulted to the literal `'Notifications'`, breaking both the uniform-input rule and the no-hardcoded-English-literal rule — and [#1598](https://github.com/tutkli/forty-cdk/issues/1598) renamed it to `ariaLabel` backed by `ForToastDefaults.viewportAriaLabel`, closing [#1401](https://github.com/tutkli/forty-cdk/issues/1401) item 1. The **input** rule now holds without exception: every reactive accessible name in the library is spelled `ariaLabel`, and none defaults to a hardcoded literal. The defaults **key** keeps the one recorded deviation above (`ForBreadcrumbsDefaults.label`), so the rule for a new piece needing a mandatory name is unchanged: `ariaLabel` + a `*AriaLabel` defaults key.

- **A piece emitting both channels must gate its `hostLabelledBy` fallback on the _resolved_ `aria-label`, not on the raw input.** `aria-labelledby` outranks `aria-label` in ARIA, so a library-generated trigger-id fallback would silently beat the consumer's adopted name. The surfaces that already suppressed their fallback when `ctx.ariaLabel()` was set now suppress it when `resolvedAriaLabel()` is set. Surfaces whose `aria-labelledby` fallback comes from a **registered title element** (dialog / drawer / popover) keep emitting both: mounting a `[for<Primitive>Title]` is itself an explicit consumer act.
- **Per-instance computed names deliberately do _not_ adopt.** `[forCalendarCell]`'s date label, `[forCarouselSlide]` / `[forCarouselIndicator]`'s positional `"N of M"`, `[forComboboxChipRemove]`'s `"Remove <chip>"`, the date/time [segment base](../../projects/forty-cdk/core/src/datetime/segment-directive.ts)'s segment name, and `[forCarouselRotationControl]`'s play/pause-swapping name are all stamped in a repeat (or swap with state), so one static attribute would name every instance identically — an authoring error rather than an override — and none of them ever resolves to `null`, so nothing is erased. The supported per-instance channel stays the reactive `[ariaLabel]` input or the scope's label builder.

**Forcing `type="button"` is a host _binding_, never a static host attribute ([#1512](https://github.com/tutkli/forty-cdk/issues/1512)).** Fifty pieces used to declare `type: 'button'` as a static host attribute, which fails in both directions. A static host attribute is stamped onto **whatever element the consumer picked**, and `type` is not a valid attribute of `<div>` / `<span>` — invalid markup, inert attribute. Worse, Angular lets a consumer's own **static** template attribute win over a directive's static host attribute, so `<button forCheckbox type="submit">` kept `type="submit"` and submitted its surrounding `<form>` on every click — silently, with correct ARIA and correct `data-state`, while the piece's own JSDoc promised the opposite. The seam is `hostButtonType()` in `core/host-attributes/host-type`, host-bound as `'[attr.type]': 'buttonType()'`: `'button'` on a native `<button>` host, `null` on anything else, one `tagName` check instead of fifty. `forty-cdk/no-restricted-syntax` fails `pnpm lint` on a static `type: 'button'` in a `host` block so the sweep cannot grow back one piece at a time.

This seam is the deliberate **inverse** of the `hostId` / `hostAriaLabel` / `hostLabelledBy` adoption above: the binding **overrides** the consumer's value rather than adopting it. A piece that forces `type="button"` is protecting against form submission, so a consumer `type="submit"` on that host is an authoring error, not an override — the whole point is that activating the control never submits. `[forButton]` is the one piece with the opposite contract and it does **not** use the seam: a `[forButton]` on a real submit button is legitimate usage, so it captures the consumer's `type` at construction and re-emits it through its own `resolvedType` (`null` on a non-button host, `'button'` on a native button with no consumer value).

**`data-highlighted` (sibling vocabulary to `data-state`).** Items that participate in roving-tabindex or `aria-activedescendant` navigation expose a boolean `data-highlighted` when they are the current keyboard-focused candidate. This is distinct from `data-state` (which reflects logical state — `checked`, `open`, etc.) and is the _only_ CSS hook combobox consumers have, since `aria-activedescendant` keeps focus on the input rather than on the option (no `:focus`). Roving-tabindex primitives expose it for parity with the activedescendant flow and for hover-uncoupled-from-focus styling. Items reflecting `data-highlighted` today: `Listbox` option, `Menu` item / checkbox-item / radio-item, `Select` option, `Combobox` option, `Calendar` gridcell.

**CSS custom properties (`--for-*`).** A primitive that computes a value the consumer's CSS needs — a measured box, a fraction, a live gesture delta — publishes it as a **CSS custom property** rather than writing the final declaration itself; writing `width` / `transform` outright would be styling, which the library does not do. The names are uniform so a consumer can guess a property from the primitive:

```
--for-<primitive>-<subject>-<quantity>[-<axis>]
```

- **`--for-` is the namespace.** Every custom property the library reads or writes carries it, and nothing else does.
- **`<primitive>`** is the entry-point name in kebab-case (`carousel`, `drawer`, `meter`, `navigation-menu`, `progress`, `slider`, `stepper`, `table`, `toast`, `tree`). It is **mandatory**: a bare `--for-<quantity>` is not namespaced enough to survive two primitives composed on one element, or to be greppable. Shared code in `forty-cdk/core` that writes on behalf of whichever primitive mounted the surface substitutes the **family** name of the machinery — `floating` for the `core/floating` positioners (`--for-floating-anchor-width`, `--for-floating-available-height`) — because no single primitive name is correct for all ~10 of its callers. A family segment is not a licence to omit the segment: it names a real shared module, and the properties under it are still subject to every rule below.
- **`<subject>`** names the piece or the measured thing, and is present only when the primitive publishes more than one quantity (`indicator`, `viewport`, `range`, `thumb`, `swipe`, `drop`, `col-<name>`). A primitive publishing a single quantity omits it — `--for-stepper-progress`.
- **`<quantity>`** is the noun: `width`, `height`, `offset`, `position`, `movement`, `progress`, `percentage`, `index`, `count`, `level`, `start`, `end`, `size`.
- **`<axis>`** is `-x` / `-y`, always last, and only when the same quantity is published per axis (`--for-toast-swipe-movement-x` / `-y`). A bare coordinate elides the quantity — `--for-navigation-menu-indicator-x` is the indicator's x position.

A templated segment is allowed where the consumer names the thing: `--for-table-col-<name>-width` interpolates the `[forTableColumnDef]` name into `<subject>`. Validate any such name before it reaches CSS — `assertColumnName` in `table/src/table-context.ts` rejects anything outside `[-_A-Za-z0-9]` precisely because a stray space or `)` produces a silently invalid declaration rather than an error.

**A property is named for the quantity, never for the caller.** A `--for-*` property written by shared code in `forty-cdk/core` is part of the library-wide styling vocabulary, so its name must describe _what the value is_, not which primitive happens to consume it today. `core/floating/item-aligned.ts` used to publish `--for-select-content-available-height` purely because Select is its only caller, while the anchored positioner already published the same quantity — the maximum block-size the surface may occupy before it collides — as `--for-floating-available-height`; a consumer switching `position="popper"` to `position="item-aligned"` had to rewrite their `max-height` recipe for no semantic reason ([#1400](https://github.com/tutkli/forty-cdk/issues/1400) item 15a). One concept gets one name across every positioning strategy. **The shared name does not imply shared arithmetic**: each strategy computes the value its own algorithm supports (anchor-relative from floating-ui's `size` middleware in `popper`; `innerHeight - 2 * collisionPadding` in `item-aligned`, where the surface overlays the trigger and the middleware clamps it into the full viewport band), and the per-strategy computation is documented on the positioner's JSDoc plus the property's row in [`docs/styling-floating-content.md`](../../docs/styling-floating-content.md). The corollary is that a strategy publishes only what it actually computes — item-aligned deliberately does **not** emit `--for-floating-available-width`, because it pins the cross axis to the trigger's left edge and has no width budget; publishing a property for symmetry alone would ship a number the algorithm never derived. A primitive-scoped name stays correct only for a property a _primitive's own_ source writes about its own anatomy (`--for-table-col-<name>-width`).

**Unit vocabulary — the suffix is the type contract.** A custom property is an untyped token, so its name is the only signal of what `var()` yields. Pick the suffix that matches the value and never mix families:

| Suffix                                                                  | Value                                                                               | Examples                                                                                                                              |
| ----------------------------------------------------------------------- | ----------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| `-width`, `-height`, `-x`, `-y`, `-offset`, `-movement-*`               | a **`px`-suffixed length string**                                                   | `--for-floating-anchor-width`, `--for-navigation-menu-indicator-x`, `--for-toast-swipe-movement-y`, `--for-carousel-swipe-movement-x` |
| `-percentage`                                                           | a **`%`-suffixed string**, drop-in for `width` / `inline-size`                      | `--for-progress-percentage`, `--for-meter-percentage`                                                                                 |
| `-progress`, `-position`, `-range-start` / `-range-end` / `-range-size` | a **unitless number in `[0, 1]`** — the consumer multiplies (`calc(var(…) * 100%)`) | `--for-stepper-progress`, `--for-drawer-swipe-progress`, `--for-slider-thumb-position`                                                |
| `-index`, `-count`, `-level`, `-per-view`                               | a **unitless integer**                                                              | `--for-carousel-active-index`, `--for-carousel-slide-count`, `--for-tree-drop-level`                                                  |

A value that is none of those publishes a complete CSS value and says so in the JSDoc; `--for-floating-content-transform-origin` (a pair of `<origin>` keywords) is the only one today. Resist the shorthand temptation in particular: the drawer's gesture displacement publishes `--for-drawer-swipe-movement-x` / `-y` as two px lengths that the consumer composes (`translate: var(--for-drawer-swipe-movement-x, 0px) var(--for-drawer-swipe-movement-y, 0px)`) rather than one `"<x> <y>"` string, so the value stays inside the `-movement-*` family and each axis is independently readable ([#1400](https://github.com/tutkli/forty-cdk/issues/1400) item 15c). It is published as a custom property rather than a direct inline `translate` because `transform` is reserved for `ForDrawerScaleCoordinator` and Angular drops a directly-written inline `translate` when the consumer also binds `[style.*]` on the same host.

**In vs out — out is the default; an input must be documented as one.** Almost every `--for-*` is an **output**: the library writes it (a host `'[style.--for-…]'` binding, or `el.style.setProperty` from a positioner / registry / gesture engine) and the consumer only reads it with `var()`. **`--for-floating-arrow-offset` is the library's only input** — the consumer sets it and the anchored positioner reads it back through `var(--for-floating-arrow-offset, 0px)` when placing the arrow. That is why every README's _CSS custom properties_ table carries a **Direction** column. A new input needs a `var()` fallback so an unset property never breaks layout, and needs a real justification: an input is a styling API the library then depends on, which is the opposite of headless.

**Cleared, seeded, or retained — state which, and mirror it in the README.** An output describing a transient measurement is **removed** when the state that produced it ends: the positioners' anchor / available vars on close (`resetFloatingStyles`, `resetItemAlignedStyles`), the carousel's `--for-carousel-swipe-movement-x` / `-y` at rest and under `prefers-reduced-motion: reduce`, a column's width on unregister. An output whose rest value is a meaningful identity is instead **seeded** and always present — the drawer's `--for-drawer-swipe-movement-x` / `-y` sit at `0px` from mount and `--for-drawer-swipe-progress` at `0`, so a `translate` / `opacity` recipe never has to rely on the `var()` fallback mid-animation. An output a leave animation still needs is deliberately **retained** through the close and recomputed on the next open; `--for-floating-content-transform-origin` is the documented case (a `scale` `animate.leave` must keep pivoting from the trigger edge). State which one applies in the property's JSDoc, and mirror it in the primitive's README table.

**Exception ledger.** One documented deviation. Nothing else may deviate silently; a new property that cannot follow the rule gets a row here in the same PR.

| Property                | Deviation                                                                            | Status                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| ----------------------- | ------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `--for-carousel-offset` | A `%` string under an `-offset` name, which the table above assigns to `px` lengths. | **Permanent.** The value is a track translation expressed as a percentage of slide size, which is exactly what makes `transform: translateX(calc(var(--for-carousel-offset) + var(--for-carousel-swipe-movement-x, 0px)))` compose a percentage-based rest position with a pixel-based live gesture delta in one `calc`. Renaming it to `-percentage` would imply the drop-in `width` semantics of Progress / Meter, which it does not have. |

`--for-table-col-<name>-width` is **not** an exception — it is the templated form of the rule (see above). The `-per-view` and `-slide-count` carousel counts are not exceptions either; they are the unitless-integer family.

**ARIA state attribute emission.** WAI-ARIA distinguishes attributes whose absence is semantically meaningful (the consumer's assistive tech knows the default) from attributes whose state machine demands an explicit `"true"` / `"false"` on every render. The library normalizes both groups:

| Attribute                                                                                                                    | Truthy value | Falsy value     |
| ---------------------------------------------------------------------------------------------------------------------------- | ------------ | --------------- |
| `aria-checked`, `aria-pressed`, `aria-expanded`, `aria-selected`                                                             | `"true"`     | `"false"`       |
| `aria-disabled`, `aria-readonly`, `aria-required`, `aria-invalid`, `aria-busy`, `aria-modal`, `aria-haspopup` (boolean form) | `"true"`     | `null` (absent) |

The first row is **always emit** — togglable widgets (toggle buttons, tabs, treeitems, comboboxes, disclosures) have a defined "off" state that screen readers must announce, so the attribute must be present with `"false"` rather than absent. A `Tree` treeitem emits `aria-checked` (always-emit, `"true"` / `"false"`, or `"mixed"` in cascade mode for a parent with some-but-not-all descendants checked) only in `selectionMode="checkbox"` and `aria-selected` only in `selectionMode="highlight"` — the two are mutually exclusive per node. The second row is **truthy-only** — a missing `aria-required` means "not required", emitting `aria-required="false"` is redundant and forces consumers to write `[aria-required="false"]` selectors that fight the spec.

Canonical Angular host bindings:

- Always-emit: `'[attr.aria-checked]': 'checked() ? "true" : "false"'`
- Truthy-only: `'[attr.aria-disabled]': 'disabled() ? "true" : null'`

Three notes for edge cases:

- `aria-haspopup` may take token values (`menu`, `listbox`, `dialog`, `tree`, `grid`); when emitted as a token it is always present (e.g. `'"listbox"'`) and the boolean rule does not apply. Only normalize the boolean form against the truthy-only column.
- `aria-multiselectable` belongs to the truthy-only group. WAI-ARIA defines its default as `false` when the role demands it (`listbox`, `tree`, `grid`), so a missing attribute is unambiguous; emitting `aria-multiselectable="false"` adds noise without changing semantics. Listbox / Combobox / Select content all follow the truthy-only rule.
- **The truthy-only rule governs the _value_, not the _applicability_ — `aria-readonly` is role-gated.** WAI-ARIA supports it on `checkbox`, `combobox`, `grid`, `gridcell`, `listbox`, `radiogroup`, `slider`, `spinbutton`, `textbox`, and inherits it into `columnheader`, `rowheader`, `searchbox`, `switch`, `treegrid` ([ARIA 1.2 §aria-readonly](https://www.w3.org/TR/wai-aria-1.2/#aria-readonly)). `role="radio"` is in neither list — its supported properties are `aria-checked` (required) plus `aria-posinset` / `aria-setsize` ([ARIA 1.2 §radio](https://www.w3.org/TR/wai-aria-1.2/#radio)) — so `[forRadio]` reflects a read-only group with the boolean `data-readonly` hook only and leaves the announcement to the `role="radiogroup"` root, which does support `aria-readonly` and already emits it ([#1393](https://github.com/tutkli/forty-cdk/issues/1393) item 13). Emitting an ARIA property on a role that does not support it is an `aria-allowed-attr` violation, not a harmless extra: check the role's supported-property list before adding any `aria-*` reflection, and pair a `data-*`-only hook with the ARIA emission on whichever piece carries a supporting role.

  `role="group"` and `role="button"` are likewise in neither list, which is why the read-only state of a **container-rooted** form primitive never announces from its own host ([#1472](https://github.com/tutkli/forty-cdk/issues/1472)). The shipped split, in full:

  | Host                                                                                                                     | Role               | Read-only reflection                                                     | Required reflection                          |
  | ------------------------------------------------------------------------------------------------------------------------ | ------------------ | ------------------------------------------------------------------------ | -------------------------------------------- |
  | `[forSlider]`                                                                                                            | `group`            | `data-readonly` only; `aria-readonly` on `[forSliderThumb]` (`slider`)   | `data-required` only (`slider` lacks it)     |
  | `[forDateField]`, `[forTimeField]`, `[forDateRangeField]`, `[forTimeRangeField]` (+ the `Start` / `End` endpoint groups) | `group`            | `data-readonly` only; `aria-readonly` on each segment (`spinbutton`)     | `data-required` only, not per segment        |
  | `[forToggleGroup]`                                                                                                       | `group`            | `data-readonly` on the root only — no supporting role in the composition | `data-required` on the root only             |
  | `button[forToggle]`, `[forRadio]`                                                                                        | `button` / `radio` | `data-readonly` only (the radiogroup root announces for `[forRadio]`)    | `data-required` only for `button[forToggle]` |

  A container whose composition has no supporting role at all (ToggleGroup) simply has no ARIA channel for the state — reflect `data-readonly` and keep the interaction guard; do not reach for an unsupported attribute to fill the gap. The behavioural guard is the shared form-control contract's `roleSupportsAriaReadonly: false` option (`src/test-utils/contract/form-control-contract.ts`), which asserts `data-readonly=""` **and** the absence of `aria-readonly`.

  **Dropping the emission is the right resolution only when another piece can announce, or nothing can. A host that is the primitive's _only_ focusable surface declares a supporting role instead ([#1542](https://github.com/tutkli/forty-cdk/issues/1542)).** `[forDatePickerTrigger]` was the tenth host of this class and the first with nowhere to delegate to: a closed date picker exposes the trigger and nothing else, so the treatment above would have lost the state outright rather than relocated it. It therefore took `role="combobox"` — legal for both properties, and already the shipped shape of its two siblings `[forSelectTrigger]` / `[forTimePickerTrigger]`, whose `aria-haspopup` token is the only difference (`dialog` vs `listbox`, both allowed for a combobox popup). Reach for a role change, not an emission drop, when the state would otherwise have no channel at all.

  The **mechanical** guard, covering every role-gated property and not just `aria-readonly` on the controls that adopt that contract, is the `forty-cdk/aria-attr-allowed-on-role` ESLint rule ([#1476](https://github.com/tutkli/forty-cdk/issues/1476)). It cross-checks every `'[attr.aria-*]'` host binding against the ARIA 1.2 supported-property table in [eslint.config.js](../../eslint.config.js), resolving the role from a static `role: '<name>'` in the same `host` block or, failing that, from a `button[…]` / `textarea[…]` selector. Global properties are supported on every role and are never reported; a dynamic `'[attr.role]'` and any role with no transcribed row are skipped rather than guessed at, so reaching for a new role cannot fail the build before its row is added. Both known incidents ([#1472](https://github.com/tutkli/forty-cdk/issues/1472), [#1393](https://github.com/tutkli/forty-cdk/issues/1393) item 13) were found by hand only after passing tests had pinned the invalid emission — add the row and let the rule catch the next one.

  **`aria-required` is gated the same way, and to a narrower set** — `checkbox`, `combobox`, `gridcell`, `listbox`, `radiogroup`, `spinbutton`, `textbox`, `tree`, inherited into `columnheader`, `rowheader`, `searchbox`, `switch`, `menuitemcheckbox`, `menuitemradio` ([ARIA 1.2 §aria-required](https://www.w3.org/TR/wai-aria-1.2/#aria-required)). Neither `group` nor `button` is in it, and `slider` is in it for neither property. So the same seven hosts that reflect `data-readonly` only also reflect `data-required` only ([#1539](https://github.com/tutkli/forty-cdk/issues/1539)): `[forSlider]`, `[forToggleGroup]`, `button[forToggle]`, and the four date/time field roots. Unlike read-only, the requirement is **not** re-announced from a child — a composite field would repeat "required" once per segment — so the field-level channel is `data-required` plus the consumer's own label / description wiring. The contract mirror is `roleSupportsAriaRequired: false`.

  **`aria-modal` is gated to `dialog` and `alertdialog`** ([ARIA 1.2 §aria-modal](https://www.w3.org/TR/wai-aria-1.2/#aria-modal)). An overlay that keeps a non-dialog role in modal mode — `[forSelectContent]` and `[forTimePickerContent]`, both `role="listbox"` — must not emit it: modality there is carried behaviorally by the modal shell's `inert` siblings and focus trap, and reflected as `data-modal` for styling only (#1539).

Consumers styling falsy state must select on **the absence** of the attribute (`:not([aria-disabled])`, `:not([aria-required])`), not on `[aria-disabled="false"]`. The breaking change in [#108](https://github.com/tutkli/forty-cdk/issues/108) enforces this across the library.

**Disabled custom-role controls stay focusable — never emit the native `disabled` attribute.** A control carrying a custom ARIA role (`role="checkbox" | "switch" | "radio" | "tab" | "option" | "menuitem"`, or a toggle `<button>` reflecting `aria-pressed`) reflects `aria-disabled="true"` (truthy-only) + `data-disabled=""` when disabled, and relies on the in-handler `effectiveDisabled()` / `disabled()` guards to make click and keyboard activation a no-op. It does **not** set `[attr.disabled]`: the native attribute drops the element from the focus order, which contradicts the APG (disabled controls must stay focusable so assistive tech announces them). Form-submit exclusion is owned by the hidden `<input>` (`injectHiddenInput({ disabled })`), not the visible custom-role element. Native `disabled` is correct only on genuine native form elements (`<input>`, `<textarea>`, `[forInput]`, `[forNumberInput]`) and real single-purpose `<button>` triggers that are not roving collection items (e.g. `[forDropdownMenuTrigger]`, `[forSelectTrigger]`). The trigger carve-out covers a disabled state the **consumer** drives through an input; it does **not** cover a state the primitive **auto-computes from its own position** and can flip while the button holds focus. A navigation button that disables itself on reaching a bound (calendar prev / next / view trigger — [#1285](https://github.com/tutkli/forty-cdk/issues/1285); carousel prev / next — [#1392](https://github.com/tutkli/forty-cdk/issues/1392) item 4) reflects `aria-disabled` + `data-disabled` with an in-handler activation guard instead, because the native attribute would eject the user's focus to `<body>` at the moment they hit the edge. Decided in [#561](https://github.com/tutkli/forty-cdk/issues/561) (D2).

**The two channels are mutually exclusive — a host reflecting native `disabled` emits no `aria-disabled` for that state ([#1455](https://github.com/tutkli/forty-cdk/issues/1455), [#1550](https://github.com/tutkli/forty-cdk/issues/1550)).** D2 said which hosts _may_ use the native attribute; it never said "and then do not also emit `aria-disabled`", so seven of the nine overlay triggers and all six native form-element hosts ended up emitting both. A host taking the native carve-out above therefore reflects `disabled` (via `reflectDisabled`, or the imperative `toggleAttribute` on an injected input) plus the `data-disabled=""` styling hook, and **no** `aria-disabled`: the HTML attribute already exposes the unavailable state through HTML-AAM, so the ARIA copy adds nothing an assistive technology reads, and two channels means two answers to "how do I style a disabled control". The rule reaches every native-`disabled` host — the nine overlay triggers (`[forDropdownMenuTrigger]`, `[forComboboxTrigger]`, `[forSelectTrigger]`, `[forPopoverTrigger]`, `[forDialogTrigger]`, `[forDrawerTrigger]`, `[forDisclosureTrigger]`, `[forDatePickerTrigger]` serving both the single and the range picker, and `[forTimePickerTrigger]`) and the six native form elements (`[forInput]`, `[forTextarea]`, `[forSearch]`, `[forComboboxInput]`, `[forNumberInput]`, `[forOtpInput]`). Four consequences worth knowing before you write the next one:

- **A `role="combobox"` trigger is on the native side, not the custom-role side.** `[forSelectTrigger]`, `[forTimePickerTrigger]` and `[forDatePickerTrigger]` ([#1542](https://github.com/tutkli/forty-cdk/issues/1542)) override the role, but the first sentence's carve-out is about **collection items and toggle buttons**, which must stay reachable so the user can traverse the group and hear that a member is disabled. A standalone trigger has no group to traverse, the HTML `disabled` attribute maps to the unavailable state regardless of the ARIA role, and native `<select disabled>` — the very control the select-only combobox pattern stands in for — leaves the tab order the same way. Decisive on behaviour: their `onClick` carries no in-handler guard, so the native attribute _is_ the activation guard; dropping it instead would let a disabled trigger open.
- **The rest of the form-control ARIA is untouched.** `aria-readonly` / `aria-required` / `aria-invalid` / `aria-busy` keep their truthy-only emission on the form-value triggers — this clause is about the disabled channel only.
- **The clause bans the _duplicate_ channel, not the attribute.** Two hosts take the native carve-out and still host-bind `[attr.aria-disabled]`, and both are correct because their ARIA expression encodes a _different_ condition than the signal reflected natively. `[forAccordionTrigger]`'s `ariaDisabled` computed returns `false` whenever the item is genuinely disabled, and is `true` only for the APG case of an expanded panel the accordion refuses to collapse (the native attribute carries `item.disabled`). `[forFieldset]` binds `'!isNativeFieldset() && disabled()'`, so a native `<fieldset>` host takes the native attribute and any other host takes `aria-disabled` — exclusive by construction. Neither ever emits both for the same state, which is the invariant. A second `aria-disabled` that means something other than "this control is disabled" is fine; a second one that merely restates the native attribute is not.
- **The rule is total, and mechanically enforced.** With the six native form-element hosts closed ([#1550](https://github.com/tutkli/forty-cdk/issues/1550)) there is no exception list left, so the syntactic scan needs no allowlist: `forty-cdk/no-doubled-disabled-reflection` reports an `'[attr.aria-disabled]'` host binding whose expression references the very signal the same class passes to `reflectDisabled(…)`. `[forAccordionTrigger]` and `[forFieldset]` fall out of the rule by that condition rather than by name. The scan covers the single-file declarative shape only: `[forOtpInput]`'s imperative `setAttr` / `toggleAttribute` pair on its injected input, and the three hosts inheriting their `reflectDisabled` call from `TextValueControlBase` (`[forInput]`, `[forTextarea]`, `[forSearch]`), both stay uncovered and are guarded by the contract helper instead. The spec-side mirror is the default `disabled` branch of `assertFormControlContract`, which asserts the native attribute, `data-disabled=""`, and the **absence** of `aria-disabled`.

**A live region declares exactly one channel — a live `role`, or the `aria-live` + `aria-atomic` pair, never both ([#1598](https://github.com/tutkli/forty-cdk/issues/1598) item 2, [#1626](https://github.com/tutkli/forty-cdk/issues/1626)).** `role="status"` implies `aria-live="polite"` + `aria-atomic="true"` and `role="alert"` implies `assertive` + `true` ([ARIA 1.2 §status](https://www.w3.org/TR/wai-aria-1.2/#status), [§alert](https://www.w3.org/TR/wai-aria-1.2/#alert)), so a host declaring both states its live-region semantics twice and leaves a reader unable to tell which one the primitive means. Which channel survives is decided by **how the region reaches the accessibility tree**, and the reason goes in the piece's JSDoc either way:

- **Inserted with its text already present → keep the role.** A live role is what screen readers read reliably on insertion. `[forComboboxEmpty]` self-hides with `[hidden]` + inline `display: none` and comes back with its message already in the DOM, `[forToast]`'s bare-error host is mounted with its content, and `[forFieldError]` likewise — all of them keep `role="status"` / `role="alert"` and emit no `aria-live`. `[forComboboxStatus]` stays mounted and only rewrites its text, so either channel would serve it; it keeps the role to match its sibling and hold one vocabulary inside the entry point.
- **Exists, empty, before its text changes → keep the pair.** `LiveAnnouncer`'s two off-screen regions are created at construction and only ever have their text rewritten, so a live role buys them nothing, and the pair states `aria-atomic` outright instead of leaving it to an implicit role mapping.
- **`[forToast]` is the one host declaring both, and its pair is a switch rather than a duplicate.** Every variant except a bare `error` routes its announcement through `LiveAnnouncer` and silences the host with `aria-live="off"`, leaving a non-live `role="status"` region behind. Both channels are therefore _bound_, and the binding is what carries the state.

The mechanical guard is `forty-cdk/no-doubled-live-region-channel`: it reads a static `role: '<name>'` from an inline `host` block and reports a static `aria-live` / `aria-atomic` whose literal value is the one that role already implies. The exemption is a condition rather than an allowlist (the [#1550](https://github.com/tutkli/forty-cdk/issues/1550) shape) — a `'[attr.role]'` binding skips the host, so `[forToast]` falls out by construction; a bound attribute, or a static value that _differs_ from the implied one (`role="log"` + `aria-atomic="true"`), is an override rather than a doubling; and a role with no row in the rule's table is skipped, so reaching for `log` / `marquee` / `timer` cannot fail the build before its row is transcribed.

**A primitive that accepts a non-native host synthesizes its own tab stop and activation — a tightened selector is not the fix ([#1471](https://github.com/tutkli/forty-cdk/issues/1471)).** An attribute selector like `[forCheckbox]` matches any element, so `<div forCheckbox>` announces `role="checkbox"` plus its `aria-checked` state to assistive tech. If the directive only listens for `(click)`, that element is keyboard-**inoperable**: there is no `tabindex`, so it is not even focusable, and nothing translates `Space` into activation. The failure is silent — every role and `aria-*` is correct, so nothing in the accessibility tree looks wrong. Route the synthesis through the shared `core/synthetic-activation` helper rather than re-deriving it per primitive:

```ts
readonly #activation = injectSyntheticActivation({ disabled: this.effectiveDisabled });
protected readonly tabindex = this.#activation.tabindex;
```

host-bound as `'[attr.tabindex]': 'tabindex()'` with `(keydown)` / `(keyup)` / `(blur)` delegating to `keydown()` / `keyup()` / `reset()`. The helper emits `tabindex="0"` only on a non-`<button>` host, returns early from every handler on a native `<button>` (the platform already synthesizes click from the keyboard, so a second path would double-activate), funnels the keyboard through `host.click()` so the primitive keeps one activation handler, activates `Enter` on keydown and `Space` on keyup, always `preventDefault()`s `Space` keydown to block page scrolling — even while disabled — and drops a half-finished `Space` press on `reset()`. Adopters today: `[forButton]` (which also emits `role="button"` on a non-native host), `[forCheckbox]`, `[forSwitch]`. A disabled host keeps its tab stop, per the focusable-when-disabled rule above.

**Restricting the selector to `button[forX]` does not fix this — it hides it.** `hostDirectives` **ignores a directive's selector**, and wrapping by composition is a path the library documents and supports (`docs/wrapping-form-primitives.md`), so a design-system wrapper composing the primitive onto a `<div>` host would still ship the announced-but-inoperable control. `button[forToggle]` is the one restricted selector left, kept because `aria-pressed` is a `role="button"` property and the primitive relies on the native element rather than synthesizing the role: it is a documented divergence, not the pattern to copy. A new form-control primitive whose host may be non-native adopts the helper.

**`model()` change emitter contract.** A `model<T>()` already exposes a `<name>Change` output that fires _only_ when the primitive itself updates the signal via `set/update`, and stays silent on consumer writes through `[(name)]`. This is the intended change-emitter contract — **do not add a parallel `output<T>() <name>Change`**, it would shadow or duplicate the implicit one. Document the contract on the `model()` JSDoc instead.

**Selection value-type contract.** Every selection primitive models its value the same way, so consumers learn one shape across the library:

- **The value model is always a `readonly` array** — `model<readonly T[]>` on the primitives generic over their item type (`ForListbox<T = string>`, `ForSelect<T = string>`, `ForCombobox<T = string>`, `ForTree<T = string>`, `ForTable<T = unknown>`) and `model<readonly string[]>` on the two whose values are DOM-ish keys rather than domain items (`Accordion` panel ids, `ToggleGroup` item values). Never expose a mutable `string[]` model; mutate it immutably internally (`[...]`, `.filter()`, `new Set()` then spread) and `set()` the new array. The array is the `FormValueControl` backing — the form contract needs a uniform multi-capable shape regardless of mode.
- **Single mode is the same array with 0–1 elements.** `multiple=false` (default) keeps the array at length ≤ 1; option activation replaces rather than appends.
- **Single-select consumers read a derived accessor, never `value()[0]`.** Each selection primitive exposes a read-only single-mode view derived with `computed()` (never an `effect`-written signal), all three built on the shared `singleSelected` helper: `selected: Signal<T | null>` on `ForSelect` / `ForListbox`, and `selectedItem: Signal<T | null>` on `ForCombobox` (its `selected` name is already taken by the value+label chip list). It returns the sole element when the array has exactly one entry, else `null` (empty, or multiple in multi mode). This is a convenience accessor, not a second source of truth — writes still go through `[(value)]`.

- **The equality comparator input is always named `compareWith`** — `input<(a: T, b: T) => boolean>((a, b) => a === b)`, matching the `compareWith` name Angular already uses on its own `@angular/forms` select controls. `ForListbox`, `ForSelect`, `ForCombobox`, `ForTable` and `ForTree` all expose exactly this input, the public context interfaces expose it as `compareWith: Signal<(a: T, b: T) => boolean>`, it is the `'compareWith'` entry in each `FOR_<PRIMITIVE>_HOST_DIRECTIVE_INPUTS` tuple that has one (Tree is not a form-value control and ships no host-directive sibling), and the shared `RangeSelectionEngineDeps` in `forty-cdk/core` names its dependency the same way. Never introduce a per-primitive variant (`isItemEqualToValue`, `equalsFn`, `itemsEqual`) — [#1400](https://github.com/tutkli/forty-cdk/issues/1400) item 1 retired the `isItemEqualToValue` spelling library-wide. The positional `equals` parameters inside the internal helpers (`core/selection`, `combobox-auto-highlight`) are function arguments, not the public input, and keep their name.

**Expansion value-type contract — the same shape, keyed by the same identity.** A primitive that models _which items of a hierarchical collection are open_ exposes `expanded: model<readonly T[]>([])`, keyed by the very value its items carry in `[value]`, always multi (there is no single mode, so no `multiple` input governs it), with the implicit `expandedChange` firing only on internal expand / collapse. Two primitives have one — `ForTable` in `mode="treegrid"` (open parent rows) and `ForTree` (open parent nodes) — and until [#1738](https://github.com/tutkli/forty-cdk/issues/1738) they disagreed: `ForTree.expanded` was `readonly string[]` on a root that was not generic at all, so the same idea needed different consumer code on each side and no helper over "expandable collections" could be typed. `ForTree<T = string>` now carries the type parameter, joining `ForTable<T = unknown>` / `ForListbox` / `ForSelect` / `ForCombobox`. The rule the fix encodes is the one to apply next time: **a primitive carries one identity vocabulary, not two** — keying `ForTable.expanded` by row id would have been the smaller diff and would have left that primitive's `value` a `readonly T[]` beside an `expanded` of ids.

- **The comparator belongs to the primitive, not to the model.** `ForTable` and `ForTree` both resolve selection _and_ expansion membership through the one `compareWith` input the selection contract mandates. A primitive that adds an expansion model reuses whatever identity its selection model already resolves with — never a second, expansion-only comparator. `ForTree` shipped without one for the length of #1738 and it was the wrong half to defer: a `T = string` default makes `===` natural but it is the generic parameter, not the default, that decides what a consumer can key by, and a primitive that accepts object values while resolving them by reference has no channel for the identity its consumer actually means. The failure is silent in the direction that matters — a `descendantsOf` returning freshly-mapped objects reports `checkState` as `'false'` on a fully-checked subtree, with nothing thrown and nothing logged.
- **Threading the comparator is where the expansion model costs more than the selection one, and the cost is concentrated in one place.** Selection membership is a handful of `isInArray` / `toggleInArray` calls; expansion additionally keys the **visible-node fold** (every node, every run) and the **cascade tri-state** (every descendant of every rendered parent), both of which were hashed `Set` lookups precisely because `===` allowed it. An arbitrary equivalence cannot be hashed, so the two live behind `treeMembership` in `tree/src/tree-identity.ts`: it hashes when the comparator is the exported default by reference and scans otherwise, which keeps every string-valued tree on the complexity it already had and confines the O(n·m) to consumers who asked for a custom comparator. Copy that shape rather than the per-call-site `some()` when a new primitive's membership probe is per-item-per-render; reach for the plain `isInArray` when it is a single lookup.
- **The pieces stay non-generic; the contract interfaces default to `unknown`.** `ForTreeContext<T = unknown>` / `ForTreeItemHandle<T = unknown>` follow `ForListboxContext`'s shape exactly: the `InjectionToken` is declared at the `unknown` instantiation and `injectTreeContext<T>` casts, so a piece written against the token still compiles while `ForTree<T>` / `ForTreeItem<T>` keep the consumer-facing inference. Do not make the token itself generic — it cannot be.

Primitives whose value is a single item rather than a collection are out of the array contract above — it covers the array-backed multi-capable controls only — but they share one rule of their own: **a single-value selection / open-item model is `model<string | null>(null)`, with `null` as the "nothing selected / nothing open" sentinel — never the empty string.** `''` is a legitimate item value, which is exactly why it cannot double as the sentinel: a consumer seeding `''` would be indistinguishable from a selection whose value happens to be empty, and every `=== ''` guard in the primitive would misread it as closed. Guard against the sentinel with an explicit `=== null` / `!== null` comparison rather than truthiness, so a genuine `''` value keeps flowing through.

**The family is derived, never enumerated ([#1725](https://github.com/tutkli/forty-cdk/issues/1725)).** This paragraph used to name its four members by hand, and the fifth is what that cost: `ForMenuRadioGroup` shipped `model<string>('')` for as long as the list read _Tabs, RadioGroup, Menubar, NavigationMenu_, so a `[forMenuRadioItem] value=""` — ordinary markup for the "None" option of a sort-order menu — announced `aria-checked="true"` with nothing selected. The failure is exactly the one the rule predicts, and it is silent: the DOM stays internally consistent, every per-primitive spec passes, and only a screen reader reports it. Two gates replace the list. [`assertSingleValueModelContract`](../../projects/forty-cdk/src/test-utils/contract/single-value-model-contract.ts) mounts an `''`-valued item deliberately and asserts the primitive rests at the sentinel, treats `''` as a selectable value distinct from it, and clears back to `null`; [`single-value-model-adopters.spec.ts`](../../projects/forty-cdk/src/lib/single-value-model-adopters.spec.ts) derives the family from source — a root declaring a non-array `model<string…>` named `value` — and fails on a member that does not adopt the contract, on a member declared with any other type argument or seed, and on one of the two free-text exclusions whose condition stopped holding. Menubar and NavigationMenu were brought onto the shape in [#1400](https://github.com/tutkli/forty-cdk/issues/1400) item 3 and MenuRadioGroup in #1725; a sixth member is caught by the roster rather than by a reviewer's memory.

A consumer-facing summary of the array contract lives in [`docs/selection-value-type-contract.md`](../../docs/selection-value-type-contract.md), which is also where the single-select form-field shape rule is documented for consumers.

**Single-mode empty selection — `ToggleGroup` vs `RadioGroup` (intentional divergence).** A single-select `ForToggleGroup` **allows the empty selection**: clicking the already-pressed item clears it back to `[]`, so the group can rest with nothing selected. This is deliberate and differs from `ForRadioGroup` / `ForTabs`, where APG single-select semantics keep exactly one item active once any has been chosen and re-activating the current item is a no-op. The divergence is correct because a toggle button group models a set of independent on/off buttons that happen to be mutually exclusive in single mode — "all off" is a valid state — whereas a radio group models a single required choice. Do not copy `RadioGroup`'s "always one selected" rule onto a new toggle-style primitive, and do not copy `ToggleGroup`'s "clearable" rule onto a new radio-style primitive; pick the one that matches the control's real semantics.

**Ordinal-position models keep a positional name — `Stepper.selectedIndex` (intentional divergence).** The selection contract above governs primitives whose model carries a **value identity** (`[(value)]`, a `string` or a `readonly T[]`). A primitive whose state genuinely _is_ an **ordinal position in a sequence** models it as a number and names it for the position: `ForStepper.selectedIndex`, `ForCarousel.activeIndex`, `ForPagination.page`. Do not normalize these to `[(value)]`. Stepper is the one worth spelling out, because it looks the most like Tabs and reuses the Tabs APG backbone:

- **The index is the quantity, not a key for one.** `[forStepperProgress]` computes `aria-valuenow` and the `--for-stepper-progress` custom property as `selectedIndex / count` (or `completedCount / count` on the `valueBy="completed"` basis). Ordinal arithmetic straight off the model is the feature; a string value would force an index lookup before any progress number could exist at all.
- **The range is the inclusive `0 … count`, and the terminal value names no step.** `selectedIndex() === count()` — one past the last step — is the **completed** state: `isCompleted()` is true, `canAdvance()` returns `false`, the one-shot `(complete)` output fires on entry, every `[forStepperContent]` goes inactive and only `[forStepperCompletedContent]` activates. There is no step for a string value to point at, so the overflow terminal is expressible only as a number.
- **`selectedIndex`, not `activeIndex`.** In `mode="interactive"` the stepper implements the APG Tabs pattern and its triggers emit `aria-selected`, so the position genuinely _is_ a selection — that is what earns the `selected` prefix. `ForCarousel.activeIndex` carries no selection semantics and `ForPagination.page` is a domain term; each name matches its own primitive rather than a house style imposed across all three.
- **Consumer consequence — indices are DOM-order positions, so reordering renumbers them.** A step's index is `[forStepper]`'s registration order of its `[forStepperItem]`s, and there is deliberately **no** `[step]` override on the item. Inserting, removing, or reordering steps changes what a given `selectedIndex` means, so a persisted index must be re-derived against the new order, never restored verbatim. `[forStepperContent]`'s `[step]` input pins a _panel_ to a step when panels are rendered or ordered independently of the items — it does not stabilise the item indices themselves. Consumers with a dynamic step list should hold their own state keyed by step identity and map to an index at bind time.

Decided in [#1400](https://github.com/tutkli/forty-cdk/issues/1400) item 10.

**Page-key vocabulary — `stepMultiplier` vs `largeStep`.** `[forSlider]` and `[forNumberInput]` express the `PageUp` / `PageDown` distance as `stepMultiplier`, a **relative** multiplier over `step` (default `10`, scope-configurable through the primitive's defaults provider), so a fractional `step` pages proportionally instead of taking a fixed absolute jump ([#1400](https://github.com/tutkli/forty-cdk/issues/1400) item 5). `[forPaneResizer]` keeps an **absolute** `largeStep` on purpose: its value is unit-agnostic (px / % / fr / rem) and is handed straight to the clamp, so there is no `step` grid to multiply against. A new primitive with a `step` grid uses `stepMultiplier`; only a unit-agnostic resizer-style control may use an absolute `largeStep`.

**Orientation + writing direction.** Primitives whose keyboard navigation has an axis expose `orientation: 'horizontal' | 'vertical'` and `dir: 'ltr' | 'rtl' | null` inputs and pass them to the shared `core/keyboard-navigation` helpers. Default to the orientation that matches the primitive's most common layout (`vertical` for `Accordion`/`RadioGroup`/`Listbox`, `horizontal` for `Tabs`). Reflect `data-orientation` on the root container so the consumer can flip CSS.

**`dir` defaults to `null` and resolves the inherited ambient direction.** The input is `input<WritingDirection | null>(null, { alias: 'dir' })` (named `_dirInput` internally), and the directive derives the effective value through the shared `injectTextDirection(this._dirInput)` helper in `core/text-direction/`: `readonly dir = injectTextDirection(this._dirInput)`. The helper returns `explicitDir() ?? <ambient>`, where the ambient value is read from the **nearest ancestor carrying a `dir` attribute** (`element.parentElement.closest('[dir]')`, normalised to `ltr`/`rtl`; `auto` and unknown tokens fall back to `ltr`), then `<html dir>`, defaulting to `'ltr'`. So a primitive dropped inside `<html dir="rtl">` (or any RTL-resolved ancestor) with no explicit `[dir]` resolves arrow-key semantics as RTL automatically; an explicit `[dir]` always wins. The helper is SSR-safe (gated on `isPlatformBrowser`, never touches `document`/`window` without a DOM, defaults to `'ltr'`) and reactive (a `MutationObserver` on `<html>`'s subtree watches `dir` so a runtime flip — e.g. a locale toggle — updates the signal). Direction is read from the semantic `dir` attribute only, **not** from CSS `direction`; consumers wanting RTL set the `dir` attribute on an ancestor (the standard `<html dir="rtl">` setup). Every primitive with a `dir` input shares this single resolver — never reimplement it per-primitive. The adopter roster is generated at the end of this file; do not re-spell it in prose.

**The raw field of an aliased input stays public, and the `_` prefix is for a reader rather than for the compiler.** `_dirInput` is the recurring instance of a general shape — an input whose effective value is a computed over a scope default or an ambient resolver, so the raw binding and the resolved signal need two names and the resolved one takes the good one. Everywhere else in the library a `_`-prefixed member says "internal" to the compiler with `protected` (`_overlay`, `_dragging`, `_dropPosition`), and a host binding reads it from inside the class regardless. The raw input field is the one member that cannot, and the half of the reason that holds unconditionally is that narrowing it **buys nothing**: TypeScript writes `protected` members into the `.d.ts` with their full type, and only TS-`private` collapses to a typeless placeholder, so `protected readonly _dirInput` emits the same bytes and freezes the same symbol. What it does buy is a break — `strictInputAccessModifiers` makes the template type-check block assign to the **field**, not to the alias, so the narrowed field fails a consumer's `[dir]="…"` binding with `TS2445`. **That option is not implied by `strictTemplates`**: it is the one member of the family that stays `false` when `strictTemplates` is `true`, so a consumer opts into it, and this repo does — explicitly, on its own line beside `strictTemplates` in the root `tsconfig.json` — which is why a `protected` sweep turns the library's own specs red rather than shipping quietly. Read the opt-in the right way round: it makes the sweep worse, not safer, because the consumers it breaks are exactly the ones who asked for the strictest checking, and everyone else gets an identical `.d.ts` for the trouble. Nor can the input be moved to an internal host directive to keep it off the root: a consumer's own wrapper spreading `FOR_<X>_HOST_DIRECTIVE_INPUTS` then fails with `NG2017`, because the inputs of a nested host directive are not re-exposed upward. So the 56 fields stay public; what the library controls is that they are a 1.0 commitment made **by decision** — `check-alias-input-surface.mjs` (eighth in `postbuild`) pins the roster in `scripts/lib/alias-input-surface.mjs`, fails on a new `_`-prefixed public member and on an entry that outlives its member, and fails outright on any `_`-prefixed public member that is **not** an aliased input, which is the case `protected` covers. Verified in [#1724](https://github.com/tutkli/forty-cdk/issues/1724), whose premise the emit itself falsifies — the `protected` members already in `dist/forty-cdk/types/` are written there with their full type.

The **resolved** `dir` is **reflected to the host via the native `dir` attribute** — the directive host-binds `'[attr.dir]': 'dir()'` (where `dir()` is the resolved signal) on that same element. A single consumer `[dir]="…"` binding therefore drives **both** keyboard meaning and visual layout, and an inherited ambient direction reflects the same way: the native attribute is what CSS `:dir()` / `[dir="rtl"]` selectors and assistive tech both read, so consumers never add a second `[attr.dir]`. Emit it always (no truthy-only `rtl` suppression) — the resolved value always carries a concrete `ltr` / `rtl`, so both values must reflect. Every primitive with a `dir` input follows this; `MenuSub` is the one piece that takes the input without running a resolver, because it inherits its parent menu's already-resolved `dir` and composes on top. **A primitive with no axis to flip takes no `dir` input at all** — `[forSeparator]` is the canonical example (a static, non-focusable divider has no arrow-key semantics and no directional layout of its own), so do not add the input for symmetry. Both rosters are generated at the end of this file.

**Output naming.** `*Change` for value/state transitions emitted by `model()`. Verb outputs (`activate`, `escapeKeyDown`, `pointerDownOutside`) for one-shot events — never `onX` (React idiom). A click / Enter / Space activation output is uniformly named `activate` across the library (`[forButton]`, the menu-item family, `[forComboboxAction]`) — do not coin a per-primitive synonym such as `action`. **An output name must never collide with a native DOM event name** (`close`, `select`, `resize`, `drag`, `toggle`, `change`, `input`, …): the collision trips `@angular-eslint/no-output-native` on any consumer re-exposing the output through `hostDirectives` (even aliased), which defeats the sanctioned wrapping story. The rule is enabled library-wide ([#814](https://github.com/tutkli/forty-cdk/issues/814)) to enforce this — pick a non-native verb (`dismiss`, `activate`, `resizing`, `swipeMove`, …) instead.

Two narrower rules sit on top of the native-event ban. **Two primitives in the same entry point must not spend the same output name on different payloads** — `[forFreeDrag]` emits `moveStart` / `moveMove` / `moveEnd` (`{ x, y }` positions) precisely so it never collides with `[forDraggable]`'s `dragStart` / `dragEnd` reorder events ([#1400](https://github.com/tutkli/forty-cdk/issues/1400) item 7). And **a verb output may collide with an existing _state_ member on the same class** — `ForOtpInput` already had a `complete()` computed when `(valueComplete)` was renamed to `(complete)` ([#1400](https://github.com/tutkli/forty-cdk/issues/1400) item 11b). Rename the state signal, not the output, and keep the emitted `data-*` attribute name stable so consumer CSS hooks survive: the computed became `filled()` while the host still reflects `data-complete`.

**Pointer-gesture vocabulary — `swipe*` for dismissal gestures, `move*` for free repositioning.** Two different gestures, two fixed vocabularies; do not invent a third or mix them within a primitive.

- **A threshold gesture that decides an outcome** (dismiss / snap) surfaces the core `attachSwipeDismiss` engine's four phases under its own names: `swipeStart`, `swipeMove`, `swipeEnd`, `swipeCancel`. Today: `[forToast]` (emitting the core `SwipeEventDetail` verbatim) and `[forDrawer]` (emitting its own richer `ForDrawerSwipeEvent` / `ForDrawerSwipeEndEvent`). Both already sit on the same core helper — Drawer previously re-surfaced those callbacks as `dragMove` / `release`, which made one engine look like two APIs and left consumers unable to move a handler between the two primitives ([#1400](https://github.com/tutkli/forty-cdk/issues/1400) item 8). A payload may be primitive-specific; the four phase names may not. The matching CSS outputs follow the same stem (`--for-<primitive>-swipe-*`), which is why `[forCarouselViewport]` — a third `attachSwipeDismiss` caller that exposes no outputs at all — still publishes `--for-carousel-swipe-movement-x` / `-y`.
- **A continuous gesture with no outcome to decide** — free repositioning, where the only result is a new position — uses `moveStart` / `moveMove` / `moveEnd`. Today: `[forFreeDrag]`, which reports coordinates and nothing else ([#1400](https://github.com/tutkli/forty-cdk/issues/1400) item 7). It cannot use `drag*`: `drag` is a native DOM event name and `@angular-eslint/no-output-native` rejects it (and every aliased re-export through `hostDirectives`), while `dragMove` would falsely imply kinship with the drag-and-drop transfer gesture below.
- **`drag*` stays reserved for the drag-and-drop transfer gesture** — `[forDraggable]`'s `dragStart` / `dragEnd`, where an item is lifted out of one container and dropped into another. Those keep their names because the drag-and-drop vocabulary (`dragStart`, `dragEnd`, `drop`, `dropTarget`) is what consumers expect from that pattern, and neither name is a native event.

**Mount/unmount and animations.** Primitives **never** apply `[hidden]` to their visible pieces. Presence in the DOM is the consumer's responsibility — they wrap the visible piece with `@if` and use Angular's native `animate.enter` / `animate.leave` for transitions. The directive's job is reactive state + ARIA + behavior; visibility is template control flow. This rule is what unblocks idiomatic Angular animations and forces a clean separation between "is open" (state) and "is mounted" (DOM).

There are two API shapes for primitives that have a visibility/open concept:

- **Free-floating overlays** (Dialog, Drawer, Toast): the instance lifecycle is decoupled from the trigger and the directive owns no `[(open)]` model. The consumer's external signal drives `@if`, and the directive emits a `(dismiss)` output with a `*CloseReason` payload when it wants to be unmounted (Escape, \*Outside, close button, programmatic). Mount == open. Setup (focus trap, scroll lock, dismissible layer, portal, inert siblings, return-focus capture) is owned by `core/modal-shell` (`injectModalShell({...})`); the directive contributes ARIA + label / description registration on top. Cleanup runs through the shell's own `DestroyRef` hook.

  ```html
  @if (open()) {
  <div forDialog (dismiss)="open.set(false)" animate.leave="fade-out">…</div>
  }
  ```

- **Trigger-anchored overlays** (Popover, DropdownMenu, ContextMenu, HoverCard, NavigationMenu, Tooltip, Combobox content, Select content): the trigger lives inside the wrapper directive and drives state, so the wrapper exposes `[(open)]` (or `[(value)]` for selection-driven content like Combobox / Select) via a `model<bool>()` / `model<T>()`. The consumer wraps the visible content piece with `@if` driven by the same signal. `data-state` reflects logical open/closed for CSS styling, but is never tied to visibility — that's `@if`'s job.

  ```html
  <div forPopover [(open)]="isOpen">
    <button forPopoverTrigger>Toggle</button>
    @if (isOpen()) {
    <div forPopoverContent animate.leave="fade-out">…</div>
    }
  </div>
  ```

- **Embedded toggle/selection** (Disclosure, Accordion, Tabs, Listbox, future ToggleGroup): same `[(open)]` / `[(value)]` shape as trigger-anchored overlays, but the content piece is part of the document flow rather than a floating layer. The visible content piece still drops `[hidden]`; the consumer wraps it with `@if` driven by the same signal.

  ```html
  <div forDisclosure [(open)]="isOpen">
    <button forDisclosureTrigger>Toggle</button>
    @if (isOpen()) {
    <section forDisclosureContent animate.leave="slide-up">…</section>
    }
  </div>
  ```

The single exception is **Tabs panels**: it's idiomatic to keep all panels mounted to preserve scroll/input state. The consumer can either `@if` per panel or simply leave them mounted and toggle visibility in CSS via `[data-state="active"]`.

Form-value primitives (`Switch`, `Checkbox`, `RadioGroup`, `Listbox` selection, `Tabs` selection) keep `[(checked)]` / `[(value)]` — that's form state, not visibility, and the rule above doesn't apply.

### Shadow DOM — one composed-tree posture ([#1586](https://github.com/tutkli/forty-cdk/issues/1586))

**Every question the overlay core asks about focus, or about "did that interaction land inside my surface?", is answered against the composed tree, through open shadow roots.** Consumers wrap these primitives in design systems, and a design system that ships any web component — an icon button, a rich editor, a third-party widget — puts shadow roots inside dialogs and drawers as ordinary markup. Angular gets there without a web component at all: `ViewEncapsulation.ShadowDom` on a consumer's wrapper renders that component's whole template into a shadow root on its host.

Read "the overlay core" as the roster at the end of this section, not as the whole library. The scope is deliberate: a primitive's own `focusout` containment check (`listbox`, `combobox`, `toast`, the date / time fields, …) reads `event.relatedTarget`, which the browser has **already retargeted** to the nearest node in the listener's own tree, so plain `Node.contains` answers correctly there and composing it would buy nothing. What is unsafe is resolving a **deep** node — `composedPath()[0]`, or a `resolveActiveElement` descent — and then asking an un-composed question about it. Five helpers in [`core/composed-tree`](../../projects/forty-cdk/core/src/composed-tree/composed-tree.ts) are the single implementation: `resolveActiveElement` (descend `shadowRoot.activeElement` from `document.activeElement`), `resolveEventTarget` (`composedPath()[0]` over the retargeted `event.target`), `composedContains` (`contains` plus a walk up through every boundary between the two nodes), `composedParentElement` (one step of a bounded ancestor walk that crosses a boundary instead of ending at it) and `composedClosest` (the same climb, delegating each level to the native `closest`). `queryFocusableCandidates` in `core/focus-trap/focusable-candidate` is the traversal counterpart, and it enumerates and `matches` in JS rather than handing `FOCUSABLE_SELECTOR` to the engine, because a shadow host is not expressible in CSS.

**The half-applied version is worse than either half, which is why this is a posture rather than a per-module judgement.** `DismissibleLayer` resolved the deep target through `composedPath()` and then asked plain `Node.contains` about it — and `contains` answers within a single node tree, so the precise node it had just resolved was exactly the one containment disowned: a press on a control inside a web component in an open overlay read as a press _outside_ the overlay rendering it, and dismissed it. `FocusTrap` was shallow on both channels and failed the other way round: `document.activeElement` reported the shadow host, the tabbable set stopped at the boundary, and Tab escaped the surface the moment the last tabbable was shadow-nested — a keyboard trap that does not trap, WCAG 2.1.2 rather than cosmetic. Same defect from both directions, and both disappear only when every module reads through the same helpers.

**The container's own shadow root counts as inside it, on both channels.** `composedContains(container, node)` already answers `true` for a node in `container.shadowRoot`, so `queryFocusableCandidates` traverses it too — before the light children — or the two would disagree and the disagreement is the expensive direction: a trap whose candidate set is empty while its containment check says focus is inside `preventDefault()`s Tab and moves nothing, freezing the keyboard rather than merely leaking it. That is the `ViewEncapsulation.ShadowDom` wrapper composing an overlay primitive through `hostDirectives` — the whole surface lives in the host's shadow root — so it is the shape an Angular consumer is most likely to hit.

**Scope, and what it deliberately does not cover.** A **closed** shadow root exposes neither `activeElement` nor `shadowRoot`, so nothing here can see into one; a consumer who needs one inside a trap supplies `initialFocus` or a `delegatesFocus` host. `injectHasFocusableContent` measures through a boundary but its `MutationObserver` cannot watch across one, so a panel whose focusable content appears _inside_ a shadow root after first render keeps the previously measured answer. And `delegatesFocus` gets no special case: the host is a candidate when it is focusable in its own right, and the browser's delegation does the rest.

**Candidate order is composed for a host that renders no `<slot>`, and only for that.** The traversal inlines each host's shadow contents at the host, which is the flattened order when the widget owns its controls — the common case. Once content is slotted the two diverge, and by more than the word "reorder" suggests: assigned nodes are visited with the light tree, _after_ the host's whole shadow tree, whereas the browser sequences them at the `<slot>`'s position. One focusable rendered after the `<slot>` is therefore enough to produce a first / last pair the real Tab cycle disagrees with — no reordering required. Closing it needs `assignedElements()` per slot, which is deliberately not paid for here; a consumer hitting it supplies `initialFocus`.

**The rule for anything new is: never mix the two.** A module that resolves a deep target owes composed containment for it, and a bounded ancestor walk — `[inert]`, `display: none`, "which root-level child hosts this owner?", "is this focus inside a managed overlay host?" — uses `composedParentElement` / `composedClosest`, so a boundary continues the walk instead of silently ending it one element short of the root it was bounded by (that one cost `InertSiblingsStack` the ability to protect a modal rendered inside a shadowed app shell: no root-level child resolved, and the fallback inerted the subtree the modal itself lived in).

**Capture sites are part of the roster, and they are easy to miss because the trap looks like it covers them.** `FocusTrap.activate()` resolves the active element itself — but only when the caller passes no explicit `returnFocus`, and every modal surface in the library passes one. The real capture is `injectModalShell`'s synchronous read (locked in before `inert` blurs the trigger, #136) and `OverlayManagerCore.resolveReturnFocusTarget` for the imperative managers, so both of those resolve, and the manager's origin classification uses `composedClosest` for the same reason: a deep capture handed to a plain `closest` would read every shadow-nested trigger as an element outside any managed overlay. Leaving them raw is not a cosmetic gap — a trigger inside a `ViewEncapsulation.ShadowDom` wrapper resolves to a host that is usually not focusable, so `focus()` is a no-op and return focus lands on `<body>`.

The consumers today are `FocusTrap`, `DismissibleLayer`, `isFocusableCandidate` / `isTabbableCandidate` — and therefore every reader of the focusable set: `findFirstFocusable`, the modal and overlay shells, `injectHasFocusableContent` — plus `InertSiblingsStack`, `injectModalShell`'s return-focus capture, and `OverlayManagerCore`'s return-focus origin. A seventh imports the helpers rather than re-deriving the walk. The executable statement of all of it is [dialog-shadow.e2e.ts](../../projects/forty-cdk-harness/e2e/dialog-shadow.e2e.ts), which cycles Tab across a real shadow boundary inside a modal dialog and presses a shadow-nested button without dismissing it.

### A trigger-anchored root inherits its positioning block, never redeclares it ([#1726](https://github.com/tutkli/forty-cdk/issues/1726))

Every root that positions a surface against a trigger exposes the **same ten floating-ui inputs** — `side` / `align` / `sideOffset` / `alignOffset` / `avoidCollisions` / `collisionPadding` / `arrowPadding` / `sticky` / `hideWhenDetached` / `clipUntilPositioned` — and the same five effective computeds over them (`side` / `align` / `sideOffset` / `alignOffset` / `collisionPadding`; the first four are the placement values a per-open override may take over, which is a smaller set than the computeds). They are declared **twice in the library and nowhere else**, and a new anchored root extends one of the two rather than copying the block:

- **`AnchoredOverlayPositioningBase`** — the general case, and what `MenuOverlayHost` extends so the four menu roots reach it.
- **`AnchoredFormValueControlBase`** — identical block on top of `FormUiControlBase`, for the five roots that are also form values (Select, Combobox, TimePicker, and both date pickers through `DatePickerBase`). It exists **only** because TypeScript has single inheritance; it is not a second design. `anchored-positioning-inputs.spec.ts` pins the two declarations character-for-character, so a member added to one and not the other fails the suite rather than drifting.

Three rules follow, and the first is the one #1726 was opened over:

- **All four placement seeds resolve from the root's own `provideFor<Primitive>Defaults`**, through the `positioningDefaults` accessor the base reads lazily. Before #1726 the base was adopted by three of thirteen roots, so `side` / `align` were scope-defaultable for Popover / Tooltip / HoverCard and not for the other ten — a design system could express "our popups align to `end`" for three primitives and discovered the other ten by trying. Every anchored `ForXDefaults` therefore carries all four keys.
- **A seed whose library fallback is _derived_ is typed nullable on that interface, and `null` is what "derive it" is spelled as.** Two exist: `ForComboboxDefaults.align` (writing direction — `'start'` LTR / `'end'` RTL, so the listbox anchors to the input's leading edge) and `ForMenuDefaults.side` (`'bottom'` on the `[forMenu]` root, writing direction on `[forMenuSub]`, which share one defaults token). The root resolves it in its own `positioningDefaults` — a getter over a `computed` when the derivation reads a signal — so what the base sees is always a settled value and a consumer-set key still wins.
- **`fallbackAxisSideDirection` stays declared per menu root**, and it is the one positioning input that legitimately does. No other anchored overlay exposes it: dropping to the perpendicular axis is a menu-specific viewport-degradation lever, so it lives on each menu primitive's own defaults beside the four shared seeds rather than widening the base to a family of one.

The adopter roster is generated in the matrices at the end of this file, as two rows: the roots that inherit the block, and the roots that declare it locally. The second row is expected to stay empty, and `pnpm check:matrices` fails on the file that fills it.

### Auto-focus hook shape

Overlay primitives expose two vetoable hooks for the imperative focus moves they perform on mount and unmount: `autoFocusOnOpen` (just before focus enters the surface) and `autoFocusOnClose` (just before focus returns to the trigger). Both deliver a `VetoableEvent`; calling `event.preventDefault()` skips the directive's focus move while leaving the rest of the lifecycle alone. The library deliberately uses two binding shapes for this single contract:

- **Free-floating overlays use `input<((event: VetoableEvent) => void) | undefined>`** — bound as a function reference: `[autoFocusOnOpen]="onOpen"`. Today: **Dialog and Drawer**, which both inherit the pair from `core/modal-shell/modal-surface-base` (plus `ForDialogManager` / `ForDrawerManager`'s `config.autoFocusOn*`, the same callback reached imperatively). The reason is reliability on the close path: either surface can be closed via a direct `open.set(false)` from the consumer, which bypasses the `(dismiss)` output entirely. The directive must still fire `autoFocusOnClose` deterministically on every close path — including the destroy hook — so it stores a function reference rather than relying on Angular's `OutputEmitterRef` lifecycle (which doesn't guarantee subscriber delivery during teardown). This is the same constraint as the teardown-callback rule two sections down.
- **Trigger-anchored overlays use `output<VetoableEvent>()`** — bound as an event listener: `(autoFocusOnOpen)="…"`. Today: **Popover, DropdownMenu, ContextMenu, Menu sub, Menubar, Select, Combobox (picker anatomy), DatePicker / DateRangePicker (through `date-picker-base`), TimePicker**, plus any future trigger-anchored overlay. These primitives always route close transitions through their own `model<bool>() open` (and therefore through the implicit `openChange` emitter), so there is no escape hatch that bypasses the output. The output shape stays idiomatic Angular and matches the surrounding dismiss outputs (`(escapeKeyDown)`, `(pointerDownOutside)`, etc.).

| Shape                               | Binding                      | Adopters                                                  |
| ----------------------------------- | ---------------------------- | --------------------------------------------------------- |
| `input<(e: VetoableEvent) => void>` | `[autoFocusOnOpen]="onOpen"` | the free-floating overlays + their managers               |
| `output<VetoableEvent>()`           | `(autoFocusOnOpen)="…"`      | the trigger-anchored overlays (Combobox picker anatomy\*) |

The per-file adopter rosters behind both rows are generated at the end of this file.

\* **Combobox exposes the hooks only in its picker anatomy.** In the editable anatomy (no `[forComboboxTrigger]`) `aria-activedescendant` keeps focus on the input the entire time — there is no imperative focus move, so neither hook fires (this was the documented "exposes neither hook" exception before [#675](https://github.com/tutkli/forty-cdk/issues/675)). Registering a `[forComboboxTrigger]` switches it to the trigger-anchored model: focus moves into the input on open and returns to the trigger on close, so `(autoFocusOnOpen)` / `(autoFocusOnClose)` fire and are vetoable exactly like the other trigger-anchored overlays (the `{move, veto}` initial-focus shape is reused via `injectOverlayShell`). Document any new overlay against this section.

**Teardown-time notifications use a function `input`, never an `output` / `model`.** The same constraint that shapes Dialog's `autoFocusOnClose` applies to any value a primitive must report from its **destroy** hook: an `OutputEmitterRef` (and therefore a `model()`'s implicit `<name>Change`) is already destroyed by then, so emitting only logs `NG0953: Unexpected emit for destroyed OutputRef` and the consumer's bound signal never updates. The sanctioned shape is a callback input bound as a function reference — `input<((value: T) => void) | undefined>(undefined)` — invoked only on the teardown path, with the JSDoc naming both the timing and the reason. Today: `[forTableColumnResizer]`'s `widthRevert` and `[forPaneResizer]`'s `valueRevert` (the pre-drag value of a drag aborted by unmount, via the core drag session's `cancelOnDestroy` — [#1425](https://github.com/tutkli/forty-cdk/issues/1425)), plus the auto-focus hooks above. Every non-teardown path keeps its normal `model()` / `output()` channel, so these callbacks stay silent on the ordinary `Escape` / `pointercancel` reverts; do not "normalize" them into outputs.

**A core helper that registers its own teardown must never close a channel the consumer completes after it ([#1587](https://github.com/tutkli/forty-cdk/issues/1587)).** `DestroyRef.onDestroy` callbacks fire in registration order, and a helper called from a constructor registers its hook _before_ the consumer that called it — [`injectModalShell`](../../projects/forty-cdk/core/src/modal-shell/modal-shell.ts) calls `injectFocusTrap()` near the top of its body and registers its own teardown at the bottom, so the helper's hook runs first on **every** close, not only on the broken ones. A helper that "just" runs the consumer's cleanup for it therefore wins a race it is not entitled to arbitrate: `injectFocusTrap`'s safety net, had it been the `deactivate({ returnFocus: false })` #1587 proposed, would have flipped the trap inactive before the shell's own `deactivate({ returnFocus: true })` ran, and that early return would have cost return focus on every correctly-written Dialog and Drawer — with the call's idempotence, the very property the issue offered as proof of safety, being exactly what makes the loss silent. Split the teardown **by channel, not by flag**: `FocusTrap.releaseKeyboardChannel()` removes the `document` listener and the `FocusTrapStack` entry — the half that is never a judgement call — and deliberately leaves the trap's active flag set, so a later `deactivate()` still performs its focus move. Both halves of that are load-bearing for a net that must survive either hook order: the state the consumer's hook gates on stays untouched, and every removal is idempotent, so the two may run in either order, or twice.

**The corollary is that no synchronous flag can tell "the consumer forgot" from "the consumer has not run yet."** A dev-mode warning when such a net fires is therefore not implementable as an `if (trap.isActive)` gate inside that hook — it reads `true` on every correct dismissal in the library. Same family of trap as [#1591](https://github.com/tutkli/forty-cdk/issues/1591)'s construction-time open-state read: a check placed one step before the state settles reports every correct use as a defect.

**The shipped gate defers past the whole chain ([#1617](https://github.com/tutkli/forty-cdk/issues/1617)).** Angular runs `DestroyRef.onDestroy` callbacks synchronously during view destruction, so a `queueMicrotask` scheduled from the net observes the settled flag: `false` for an owner that deactivated — on either hook order — and `true` only for one that never did. Because the net deliberately leaves the flag set, that later read needs no extra bookkeeping. Two properties are load-bearing for anything copying the shape. **Both halves of the gate are read in the hook itself**, not in the microtask: `isDevMode()` and the "was it even active" flag, so a production build schedules nothing and a trap that was never activated costs nothing. And **the residual false positive is an owner that deactivates asynchronously** — nothing in the library does, and a surface deferring its close focus move past the destroy tick has already lost return focus for the reason the warning names. The check stays module-private in `core/focus-trap` because `injectFocusTrap` is the only net today; `injectDismissibleLayer` and `InertSiblingsStack` have the same hook order, and the second one to want a net extracts a shared helper rather than copying this one.

**No `forceMount` / `keepMounted` equivalent for overlays.** The library deliberately does **not** ship a `forceMount` / `keepMounted` opt-in on overlay content directives (`[forDialog]`, popover / tooltip / hover-card / dropdown-menu / context-menu content). Mount == open is structural for these primitives — focus trap, scroll lock, body inert, dismissible layer push, and ARIA modality all hang off the directive's lifetime via `afterNextRender` + `DestroyRef`. Splitting "alive" from "open" would require re-gating every side effect on a separate `open()` signal and inherits a long tail of subtle lifecycle bugs. The single bona-fide use case (handing exit animation control to JS animation libraries) is already covered by `animate.leave` + `@if`, so the consumer never needs the directive to outlive the open state. Revisit only if a real consumer brings a use case `animate.leave` cannot cover; design constraints if accepted are recorded in [#72](https://github.com/tutkli/forty-cdk/issues/72).

**Because the `@if` is the whole contract, a surface that is missing one says so — `warnIfMountedWhileClosed` ([#1591](https://github.com/tutkli/forty-cdk/issues/1591)).** Forgetting the `@if` is the library's quietest first-use mistake: the surface renders permanently, `data-state="closed"` is reflected onto a visible element, the ARIA stays internally consistent and the primitive keeps working, so the consumer reads it as a CSS bug and goes looking in their stylesheet — and concludes the animation support does not work, because `animate.enter` / `animate.leave` never fire on a node that never mounts. The core helper warns once per instance, dev mode only, and registers no render hook at all in a production build (`isDevMode()` gates before the `afterNextRender`). The **adopter roster is generated** into the matrices at the end of this file, alongside the `aria-hidden` + `inert` roster it is the complement of; three things about the design are worth knowing before adopting a new surface or reading a report:

- **The check is mount-time, and reads the open state inside `afterNextRender`.** Not "at construction", which the issue proposed: a piece registering with its parent from its constructor may derive its open state from an input the consumer has not written yet (`[forNavigationMenuContent]` reads its owning item's value, an `input.required`), so a construction-time read answers NG0950 instead of `false`. Deferring one frame also makes the check inert on the server and leaves the **exit-animation window** silent, which is the point: a surface the consumer closed is legitimately mounted-and-closed for as long as `animate.leave` holds the node, so re-checking on close would report every correctly wired overlay in the library. The accepted cost is a false negative — a surface that mounts open and is then left mounted forever goes unreported.
- **The report has to name a piece and a condition the consumer can find in their own template, which is a per-adopter obligation rather than a shared string.** Two adopters cannot answer it with a literal. `[forMenuContent]` also matches `[forMenuSubContent]`, and the two sit on different roots — a submenu reported under the alias it was not written as, told to wrap itself in `@if (menu.open())` when its own root is `#sub="forMenuSub"`, sends the consumer looking for markup that is not there — so the piece resolves from the host's own attribute. `[forNavigationMenuContent]` compares against its owning item's value, so `condition` accepts a **thunk**, resolved inside the same render hook where that `input.required` is finally readable; a literal there could only ship a `'<value>'` placeholder. The rule of thumb: whatever the primitive's README puts in the `@if`, the report quotes back verbatim, and `mounted-while-closed-adopters.spec.ts` asserts that per adopter so the two cannot drift.
- **Mount == open is not universal, so the roster is a judgement per piece and the exclusions are load-bearing.** The always-mounted panel family is excluded _because_ the library blesses the shape: Tabs / Stepper / Carousel panels plus Accordion and Disclosure content all reflect `aria-hidden` + `inert` while closed precisely so a consumer can drop the `@if` (see the _Inactive panels_ carve-out below), and so are the self-hiding pieces with no consumer-observable closed state. So is `[forMenuContent]` under `[forMenubar]`, whose README lists an unconditionally mounted surface as one of three supported mount shapes — the directive is shared with DropdownMenu / ContextMenu / MenuSub, where mount == open is structural, so the opt-out is a property of the **root** (`ForMenuContext.allowsUnconditionalMount`) rather than of the piece. A warning on any of these would be unsuppressable noise on markup the library recommends, which is the failure mode to weigh before extending the roster: there is no consumer-facing input to silence it.

**Defaults providers.** Primitives that expose injector-scoped defaults (cadences, offsets, hotkeys, etc.) follow a fixed convention so consumers can predict the API without reading each primitive:

- The provider helper is named `provideFor<Primitive>Defaults(overrides?)`. Always present-tense, always plural `Defaults`, always the `For` prefix (e.g. `provideForTooltipDefaults`, `provideForHoverCardDefaults`, `provideForToastDefaults`). Returns `Provider[]` so callers can spread per-scope companions (a `<Primitive>Coordinator`, etc.) into the same array.
- The injection token is `FOR_<PRIMITIVE>_DEFAULTS` (e.g. `FOR_TOOLTIP_DEFAULTS`, `FOR_HOVER_CARD_DEFAULTS`).
- The defaults shape lives in `<primitive>/<primitive>-defaults.ts`, and is exported as a named interface following `For<Primitive>Defaults` (e.g. `ForToastDefaults`, `ForDialogDefaults`). The `forty-cdk/require-defaults-sibling` ESLint rule in `eslint.config.js` requires this sibling **only when the primitive actually injects `FOR_<PRIMITIVE>_DEFAULTS`** (some non-defaults source file in the entry's `src/` references the token) — a primitive that consumes scoped defaults without the sibling fails `pnpm lint` (and therefore CI).
- The merge / inheritance behaviour is owned by the single helper at `core/defaults/defaults.ts` (`createDefaults<D>(name, fallback)` returning the `{ token, provideDefaults }` pair). Per key it picks `overrides[k] ?? parent[k] ?? fallback[k]`, where the parent is read via `[[new SkipSelf(), new Optional(), TOKEN]]` so component-level overrides layer on top of app-level overrides on top of the library fallback. Don't hand-write the `useFactory` / `SkipSelf` plumbing in primitive code; route it through `createDefaults` so the inheritance semantics stay identical everywhere.
- **The fallback is exported, always, as `FOR_<PRIMITIVE>_FALLBACK_DEFAULTS`** — a module-private `const FALLBACK` is exactly how eight primitives (`breakpoints`, the four date / time fields, `dialog`, `drawer`, `toast`) stayed out of the contract spec until [#1627](https://github.com/tutkli/forty-cdk/issues/1627). `core/defaults/per-primitive-defaults.spec.ts` pins three things per provider: the fallback resolves at the root injector, it still does under `provideZonelessChangeDetection()`, and a per-key override merges over the fallback leaving every other key intact. The third is the one that catches a real regression — `createDefaults` resolves `overrides[k] ?? parent[k] ?? fallback[k]` per key, so a defaults file that hand-rolls part of its plumbing, or an interface whose optionality drifts from its fallback, silently starts dropping sibling keys on any override. The export costs the consumer nothing: it is **not** re-exported from the primitive's `public-api.ts`, and its JSDoc says so. **A missing case is invisible rather than red** (a primitive is simply absent from the suite), so the spec derives the expected provider set from source with the same extraction the generated `defaults providers` matrix uses — a fortieth defaults file nobody wrote a case for turns it red, and so does a case naming a provider that no longer ships.
- **The interface is the resolved shape and the provider takes `Partial<…>`.** The token always holds a fully-populated value, so `For<Primitive>Defaults` declares its keys **required** and `provideFor<Primitive>Defaults(defaults: Partial<For<Primitive>Defaults> = {})` is what accepts a partial override. Only a key with genuinely no default stays optional (`ForDialogDefaults.animateEnter` / `animateLeave` / `backdropAnimateLeave` and their drawer twins — absent from the fallback, so "unset" is a real state). Do not ship a second, module-private "resolved" interface to carry the required shape: toast did, which left `FOR_TOAST_DEFAULTS` typed with a name no consumer could import, and #1627 folded it back into `ForToastDefaults`. `provideForBreakpointsDefaults(breakpoints: BreakpointMap)` is the one provider that is not a partial — its single key is a map replaced wholesale — and the contract spec adapts it with a lambda rather than bending the shared case shape.
- A `<primitive>-defaults.ts` sibling exists **only when the primitive has real per-scope tunables** it injects and consumes. Primitives with no tunables omit the file entirely — no empty stub. When a primitive later gains its first tunable, add the sibling (`provideFor<Primitive>Defaults` + `FOR_<PRIMITIVE>_DEFAULTS` + the populated `interface`) and inject the token where it's read. The reverse is enforced too: `forty-cdk/no-unused-defaults-sibling` fails `pnpm lint` on a shipped `<primitive>-defaults.ts` whose exported token no non-defaults, non-spec sibling in the entry ever injects — a dead defaults file that still enlarges the public API. (The token is read from the file's own `export const FOR_<X> = token;`, so entries whose token drops the `_DEFAULTS` suffix and secondary defaults files are handled correctly. The entry barrel — `public-api.ts`, or the legacy `index.ts` — is not counted as a consumer: it re-exports the token by name in every entry, but re-exporting is not injecting, and counting it would let a dead-but-public defaults file slip through.)

**Imperative overlay manager `class` / `classList` config.** Every imperative overlay manager (`ForToastManager`, `ForDialogManager`, `ForDrawerManager`, and any future `For<Primitive>Manager` that creates its overlay host with `document.createElement`) exposes optional `class` / `classList` on its open / show config and applies the resolved tokens to the **overlay root** — the real `[for<Primitive>]` host that carries `data-state` / `data-side` / the directive's own bindings. This exists because the programmatic host is created class-less and the literal `[for<Primitive>]` attribute selector is absent (the directive is attached via `hostDirectives`), so a consumer otherwise has no node to style and the workarounds leak internals (reaching `inject(FOR_…_CONTEXT).hostElement.classList.add(...)` or classing a child wrapper). Both fields are resolved through the single shared helper `resolveConfigClass` in `core/overlay-manager/` — never re-implement the token de-dup / merge per manager. The resolved class is set on the host (`hostEl.className = …`) **before** the directive is attached, so it composes with, and never clobbers, the directive's own host attributes. `class` is a single string (or space-separated); `classList` is an array or space-separated string; both merge and de-dup. Omitting both leaves the host with no consumer class.

**Overlay-nesting LIFO stacks are root-scoped DI services, never module-level** — `FocusTrapStack` and `DismissibleLayerStack` both store their "topmost overlay" registry in a `providedIn: 'root'` service so it is instantiated per application injector and GC'd with it (no stale stack survives `TestBed.resetTestingModule()` / micro-frontend bootstraps, and no leak between concurrent SSR requests). They stay two services on purpose: `DismissibleLayerStack` centrally owns the shared `document` listeners, whereas each `FocusTrap` owns its own keydown listener and only consults `FocusTrapStack` to decide if it is topmost (so the latter needs no `DOCUMENT` / `PLATFORM_ID` / `DestroyRef`).

**Intentional exceptions to the headless rules.** A few primitives knowingly break a project-wide rule because the underlying behaviour can't be modelled any other way without making the consumer's life worse. Any new exception MUST be added here with rationale before merge:

- **`ScrollAreaViewport` injects global CSS.** The viewport is the only piece in the library that ships a `<style id="for-scroll-area-hide-native">` tag (appended once on first construction) to hide the native scrollbars on `[forScrollAreaViewport]`. The synthetic scrollbars are the entire point of the primitive, so without this the consumer would always see double bars; pure inline styles can't target the platform-specific pseudo-elements (`::-webkit-scrollbar`, `scrollbar-width`). The injected sheet is keyed by id so multiple bundles can't double-insert it.
- **`ScrollAreaScrollbar` and `ScrollAreaCorner` self-hide when their axis has no overflow — except under `type="always"`.** The scrollbar has no logical presence when its axis doesn't overflow (there is no scrollbar to render), and the corner has none when fewer than two scrollbars are visible — keeping either mounted-but-empty would still occupy grid space and bleed into the consumer's layout. Because there is no consumer-meaningful "closed" state to wrap with `@if`, each directive hides itself: it reflects the `hidden` attribute (a11y-tree removal) **and** an inline `'[style.display]': '<visible>() ? null : "none"'` (`painted()` on the scrollbar, `visible()` on the corner) so a consumer's class-level `display: flex` can't leak through (an author selector ties with the user-agent `[hidden] { display:none }` rule and the author wins; an inline style beats any author selector short of `!important`). **`type="always"` is the documented carve-out** ([#480](https://github.com/tutkli/forty-cdk/issues/480)): it suppresses this self-removal so both tracks and the corner stay painted and `data-state="visible"` regardless of overflow (a stable, always-present track), which is why the scrollbar gates removal on `painted = type === 'always' || hasOverflow()` rather than `hasOverflow()` alone and the corner short-circuits `true` for `always`. The carve-out touches only the removal path; the `hover` / `scroll` fade (which flips `data-state` and is styled away with `opacity`, not removed) is untouched. These are the only primitive pieces in the library that hide themselves this way; the rule still stands for everything else. The same inline-`display` guarantee backs the other self-hiding pieces — `[forComboboxClear]`, `[forComboboxEmpty]`, `[forListboxOptionIndicator]` (see [#296](https://github.com/tutkli/forty-cdk/issues/296)), and `[forMenuItemIndicator]` (the checkmark/dot slot inside `[forMenuCheckboxItem]` / `[forMenuRadioItem]`, which has no consumer-meaningful "unchecked" state to wrap with `@if`; guard added in [#406](https://github.com/tutkli/forty-cdk/issues/406)). The scrollbar's guard was added in [#393](https://github.com/tutkli/forty-cdk/issues/393) to bring it in line with the corner.
- **Inactive panels reflect `aria-hidden="true"` + `inert`.** The "Mount/unmount and animations" rule above says primitives never apply `[hidden]` to their visible pieces — presence is the consumer's job via `@if`. The panel pieces honour that (none sets `[hidden]`), but additionally reflect `aria-hidden` and `inert` on the panel host while the panel is not the active one. This lets consumers _opt out_ of `@if` and keep a panel mounted-but-inactive (for CSS-only transitions, to preserve internal state, or because the pattern wants every panel mounted at once) while staying a11y-correct: the inactive panel leaves the accessibility tree and the focus order automatically. Consumers using `@if` still get the same behaviour for free during the brief mounted window before unmount.

  This is a **shared** convention, not a Disclosure carve-out: every piece whose "closed" state is a sibling-of-N or an open/closed toggle over projected content emits the pair — the roster is generated at the end of this file (Disclosure, Accordion, Tabs, Stepper content + completed content, and Carousel's off-view slides). Two things to keep straight when adding a piece: the gating signal is the piece's own activeness (`selected()` / `current()` / `inView()`), never a mount flag; and `inert` alone is not enough, because a screen reader still reaches an `inert` subtree in browse mode. Emit both or neither.

- **`injectVirtualizer` (virtualization) implements no WAI-ARIA APG pattern and owns no DOM.** Virtual
  scrolling is a rendering-performance technique, not a UI pattern — it has no role, no keyboard
  interaction and no ARIA state of its own, so the project rule "declare which APG pattern you
  implement before writing code" has no answer here. It is the library's one deliberate **headless
  windowing core** (`injectVirtualizer(options)` returning `virtualItems()` / `totalSize()` +
  `scrollToIndex` / `scrollToOffset` / `measureElement`), backed by the internal-only
  `@tanstack/virtual-core` dependency (treated like `@floating-ui/dom`: regular dependency in
  `allowedNonPeerDependencies`, tree-shaken out of non-virtualizing bundles). Unlike every other
  primitive it is not a decorator on consumer markup — the consumer renders the window themselves with
  their own `@for` and applies the position transform. Its a11y responsibility is inverted: instead of
  adding semantics it must avoid destroying the virtualized content's semantics, so consumers keep the
  screen-reader counts correct by binding `aria-setsize` (the true total) and `aria-posinset`
  (`item.index + 1`) on each rendered row. SSR-safe by returning an empty window + estimate total
  off-browser. See [#782](https://github.com/tutkli/forty-cdk/issues/782).
- **`injectBreakpoints` (breakpoints) implements no WAI-ARIA APG pattern, owns no DOM and ships no
  directive at all.** It is the same species of exception as `injectVirtualizer` — a headless
  composable, not a UI pattern: `injectBreakpoints()` returns `up` / `down` / `between` / `only`
  signal factories over `injectMediaQuery`, so it has no role, no keyboard interaction, no ARIA
  state and no host to decorate, and "declare which APG pattern you implement before writing code"
  has no answer. It differs from `injectVirtualizer` in one way worth stating: virtualization at
  least has an inverted a11y responsibility (don't destroy the windowed content's semantics), while
  breakpoints has **none** — it answers a media query and nothing more, which is why it is the one
  entry point in the library with no accessibility surface to audit. SSR-safe by resolving every
  query to `false` off-browser rather than touching `window.matchMedia`. Its consumer-facing
  `injectBreakpoints` export is the _consumer composable_ tier of the resolver taxonomy below.
- **`[forVirtualViewport]` + `*forVirtualFor` (virtualization Shape A) are the library's only
  layout-owning directive and only structural directive.** Every other primitive decorates
  consumer markup without creating or positioning DOM; this opt-in pair deliberately does both,
  because virtualization cannot be expressed by decorating existing markup — the layer must own
  the scroll viewport, the total-size sizer, and the absolutely positioned window. The viewport is a
  **component** (not a plain directive) exposing both an element selector (`<for-virtual-viewport>`)
  and the attribute form (`[forVirtualViewport]`) — the element selector is the documented "injects
  its own structure via content projection" exception — so it renders the sizer as a declarative,
  hydration-safe template node (`<div [style.height]="totalSize()">`) and projects the consumer's
  rows through `<ng-content>`; it forces `overflow: auto` on the host and builds the
  `injectVirtualizer` core internally. `*forVirtualFor` is the library's only structural directive:
  it owns a `ViewContainerRef`, renders one embedded view per `virtualItem()`, and imperatively sets
  each row's `position: absolute` + `transform: translate{X,Y}(start)` and its `aria-setsize` (true
  total) / `aria-posinset` (`index + 1`). It is also the one place the library uses `ngOnInit`: the
  core reads `orientation` / `overscan` once at construction, so the viewport defers `injectVirtualizer`
  to `ngOnInit` (via `runInInjectionContext`), where bound inputs are available yet the core's
  `afterNextRender` still registers before the first render. Built entirely on the Shape B core — no
  change to `injectVirtualizer`'s public API. See [#856](https://github.com/tutkli/forty-cdk/issues/856).
- **`[forFreeDrag]` (drag-drop) implements no WAI-ARIA APG pattern and owns no role / ARIA state.**
  "Freely reposition an element by pointer drag" is an interaction / behaviour convenience, not a UI
  pattern — like `injectVirtualizer` it has no role, no keyboard interaction and no ARIA state of its
  own, so the project rule "declare which APG pattern you implement before writing code" has no
  answer here. It is pointer-only (matching CDK's `cdkDrag` free-drag), reflecting only the
  `data-dragging` / `data-disabled` styling hooks and writing a `transform: translate(...)` on the
  moved element (the host, or a resolved `rootElement` ancestor). Its a11y responsibility is
  inverted: instead of adding semantics it must **not destroy** the moved element's semantics — the
  consumer keeps the moved element fully operable at its default position (a repositionable dialog
  stays usable by keyboard); dragging is a pointer convenience, not the only way to use it. SSR-safe
  by gating all DOM resolution, transform writes and pointer-session setup on `isPlatformBrowser`.
  See [#1020](https://github.com/tutkli/forty-cdk/issues/1020).
- **`<for-table-body>` (table) is an element-selector component that owns the column grid track.**
  The declarative column layer over `[forTableCell]` / `[forTableHeaderCell]` ([#1330](https://github.com/tutkli/forty-cdk/issues/1330)):
  it harvests `[forTableColumnDef]`s and stamps the header + data rows, so — like `[forVirtualViewport]` —
  it uses an **element selector** (`<for-table-body>`, the documented "injects its own structure via
  content projection" exception) and owns a slice of **layout** the headless core deliberately avoids:
  it sets `display: grid` + the derived `grid-template-columns` track (from each def's `width` and the
  published `--for-table-col-<name>-width` resize var) on the header row and every data row, because
  owning the track string is the entire point of the ergonomic layer. Its own host is `display: contents`
  so it introduces no box between `[forTable]` and its rows. All other styling stays the consumer's off
  the `data-*` / role hooks. It stamps consumer `<ng-template>` content through `ngTemplateOutlet` with
  `[ngTemplateOutletInjector]` set to the stamped cell's injector, so row-context primitives placed in a
  cell template (`[forTableRowSelector]`, …) resolve their `[forTableRow]` despite the template being
  declared outside any row. When `[forTableVirtualized]` is present it also owns the virtualization
  **sizer**: it reads the window published on the table context (the additive `virtualWindow` /
  `registerVirtualWindow` seam on the internal registration surface, symmetric with
  `registerVirtualNavigation` — so `forty-cdk/table` still never imports `forty-cdk/virtualization`), sizes the data rowgroup to the full scroll height
  (`position: relative` + `height`), renders only the windowed slice indexed into `rows`, and absolutely
  positions each row (`translateY`). Full-span **row variants** (`[forTableRowDef]` + `[forTableRowCellDef]`, matched
  per datum by a `[when]` predicate — group headers / separators / summary rows) are stamped as a single
  presentational cell spanning `grid-column: 1 / -1` with the row `role` + `aria-colindex="1"` +
  `aria-colspan`; the spanning cell is deliberately **not** a `[forTableCell]` and registers no cell
  handle, so the roving grid stays rectangular (arrow keys step over variant rows) — variant rows are
  non-selectable but still count towards `aria-rowindex` / `aria-rowcount`.
  See [#1330](https://github.com/tutkli/forty-cdk/issues/1330). When a `[forTableColumnDef]` is
  `reorderable` ([#1350](https://github.com/tutkli/forty-cdk/issues/1350)) the body stamps
  `[forTableColumnReorder]` on the header row and `[forDraggable]` on each reorderable header cell and
  re-emits `columnReorder`; because a directive can only be applied from the template of the component
  that lists it in `imports`, `ForTableBody` **statically imports `forty-cdk/drag-drop`** — so every
  `<for-table-body>` consumer bundles it (~14 KB gz) even with no reorderable column. This is a
  deliberate, documented coupling (the spike decision on #1350): the earlier `@defer` idea cannot
  code-split a sibling directive out of a published ng-packagr FESM, so isolation is unachievable
  together with the unified-def API. The raw `[forTableCell]` / `[forTableHeaderCell]` primitives stay
  the drag-drop-free path. Per-entry-point tree-shaking is otherwise intact (a table that never imports
  `ForTableBody` pulls neither it nor drag-drop).
